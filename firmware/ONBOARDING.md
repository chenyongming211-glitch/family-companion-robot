# Factory ESP32-S3 onboarding candidate

This is an isolated candidate workflow for new Waveshare/M5 ESP32-S3 units. It does not flash devices or replace the current standard firmware builds. Real phone/device interoperation remains a separate acceptance step.

Use the cloud server for dependencies, tests, builds and private factory material. Never put factory bundles, NVS images or generated firmware into Git or copy them onto the Mac. No C3 target is supported.

1. Obtain the exact IDF/extra-component sources and S3 submodule revisions recorded in `onboarding.lock.json`. Install IDF v6.1.0 tools for ESP32-S3 in an isolated directory. The `lib_esp32c3_family` SDK submodule also contains the S3 BLE controller; its name does not imply C3 product support.
2. Prepare a fresh source tree using `tools/prepare_experiment.py`, then run `tools/prepare_onboarding.py --tree TREE --idf-source IDF --extra-source EXTRA`. The second step verifies official component bytes, copies project-local protocomm/network_provisioning/json_generator, applies bounded20byte framing, adds factory-only integration and loads `dependencies.onboarding.lock`. It refuses an already configured tree.
3. Source that IDF environment and run existing `scripts/build.py` in TREE for `m5stack/stopwatch --name m5stack-stopwatch-xiaoman --language zh-CN --zip` or `waveshare/esp32-s3-touch-amoled-2.16 --name esp32-s3-touch-amoled-2.16-xiaoman --language zh-CN --zip`. Preserve generated `.family-onboarding-source.json` alongside private build evidence. Do not automatically flash.
4. For trusted factory preparation only, install exact `esp-idf-nvs-partition-gen==0.3.0`, obtain the hash-locked official SRP Python files described in the protocol-vector README, then run `tools/provision_factory_nvs.py --bundle PRIVATE_BUNDLE --output NEW_PRIVATE_IMAGE --official-srp OFFICIAL --idf-source IDF`. Input must be0600, output parent0700; output is0600/exclusive. This creates a0x4000 NVS image containing factory MAC/key/SRP salt/verifier. It is intended for new units and would overwrite existing NVS if flashed; this tool never flashes. The raw QR claim code is not stored in the image. The trusted provisioning CLI and device image must come from the same factory bundle.

Factory namespace presence selects the new path. Missing/malformed values within that namespace fail closed and never redirect to an official vendor cloud. BLE advertises `FAMILY_<MAC>` for at most180seconds, requires official Security2 patch1, and accepts only encrypted id/challenge before WiFi configuration. WiFi success is not binding success: device independently confirms through authenticated HTTPS, then uses fixed own bootstrap/WSS with factory Bearer key. Lost activation receipt can be recovered with authenticated bootstrap on saved WiFi after reboot.

The candidate checks CA chain, hostname and certificate dates. Factory path uses bounded SNTP before TLS and reports an error when time cannot be synchronized. Certificate-date checking is a global SDK option: the compiled legacy branch keeps its old routing but has no new SNTP initialization. Therefore this factory candidate must not be advertised as a verified update for already deployed legacy devices. Current deployed firmware is untouched.

The protocol fixture is synthetic and cross-checked against unmodified official Espressif Python. The framing adapter is a vendor transport patch; it changes no SRP, protobuf or AES-GCM bytes. Tests/builds cannot establish real iOS/Android BLE compatibility, credential persistence/reset behavior, wireless coexistence/audio performance, physical playback or production provisioning readiness.
