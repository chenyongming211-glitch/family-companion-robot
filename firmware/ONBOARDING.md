# Factory ESP32-S3 onboarding candidate

**NEW FACTORY FULL FLASH ONLY.** This is an isolated candidate workflow for new Waveshare/M5 ESP32-S3 units. It is not an OTA or app-only update for existing boards. It does not flash devices or replace the current standard firmware builds. Real phone/device interoperation remains a separate acceptance step.

Use the cloud server for dependencies, tests, builds and private factory material. Never put factory bundles, NVS images or generated firmware into Git or copy them onto the Mac. No C3 target is supported.

1. Obtain the exact IDF/extra-component sources and S3 submodule revisions recorded in `onboarding.lock.json`. Install IDF v6.1.0 tools for ESP32-S3 in an isolated directory. The `lib_esp32c3_family` SDK submodule also contains the S3 BLE controller; its name does not imply C3 product support.
2. Prepare a fresh source tree using `tools/prepare_experiment.py`, then run `tools/prepare_onboarding.py --tree TREE --idf-source IDF --extra-source EXTRA`. The second step verifies official component bytes, copies project-local protocomm/network_provisioning/json_generator, applies bounded20byte framing, adds factory-only integration and loads `dependencies.onboarding.lock`. It refuses an already configured tree.
3. Source that IDF environment and run existing `scripts/build.py` in TREE for `m5stack/stopwatch --name m5stack-stopwatch-xiaoman --language zh-CN --zip` or `waveshare/esp32-s3-touch-amoled-2.16 --name esp32-s3-touch-amoled-2.16-xiaoman --language zh-CN --zip`. Preserve generated `.family-onboarding-source.json` alongside private build evidence. Do not automatically flash.
4. For trusted factory preparation only, install exact `esp-idf-nvs-partition-gen==0.3.0`, obtain the hash-locked official SRP Python files described in the protocol-vector README, then run `tools/provision_factory_nvs.py --bundle PRIVATE_BUNDLE --output NEW_PRIVATE_IMAGE --official-srp OFFICIAL --idf-source IDF`. Input must be0600, output parent0700; output is0600/exclusive. This creates a board-matched NVS image (M5:0x4000, Waveshare:0x6000) containing factory MAC/key/SRP salt/verifier. It is intended for new units and would overwrite existing NVS if flashed; this tool never flashes. The raw QR claim code is not stored in the image. The trusted provisioning CLI and device image must come from the same factory bundle.

Factory namespace presence selects the new path. Missing/malformed values within that namespace fail closed and never redirect to an official vendor cloud. BLE advertises `FAMILY_<MAC>` for at most180seconds, requires official Security2 patch1, and accepts only encrypted id/challenge before WiFi configuration. WiFi success is not binding success: device independently confirms through authenticated HTTPS, then uses fixed own bootstrap/WSS with factory Bearer key. Lost activation receipt can be recovered with authenticated bootstrap on saved WiFi after reboot.

## Waveshare offline screen

The unactivated Waveshare candidate also requires its matching private `screen_code` NVS blob. Generate it on the cloud server with the existing [mini-program code tool](../tools/onboarding_mini_code.md), `--format screen`, then pass `--screen-code PRIVATE_SCREEN` to `provision_factory_nvs.py` alongside the same private bundle. Install the pinned `tools/onboarding_screen_requirements.txt` only in the cloud tool environment. Default image generation and M5 NVS inputs remain compatible; M5 does not accept the Waveshare screen option.

The FRC1 blob is exactly9848bytes: magic, LE16 width/height280, device_id36, LE32 payloadCRC32, and9800bytes of MSB-first black=1 bits. Both supply and firmware validate identity, dimensions, length and CRC. This is an official platform mini-program-code image converted without resizing; it is not a locally generated generic QR. No AppSecret or raw claim string is stored in NVS. The image itself contains a first-claim credential, so protect it like the factory bundle; never commit or download real code artifacts to the Mac.

Before advertising BLE, unactivated Waveshare rejects missing/corrupt/wrong-device screen material and shows a configuration error. Valid material is displayed offline until credentials arrive, with separate Wi-Fi, clock, cloud-confirmation, retry and timeout messages. Only independent activation or authenticated recovery shows success; the code is hidden during confirmation and on completion. The success page returns to the robot after2seconds. Already-activated boot does not expose the one-time code. A dedicated static30px Noto Sans CJK SC glyph subset provides these fixed messages before network assets load; its source and SIL OFL notice are in `overlays/onboarding/family_setup_font.c` and `font-license.txt`. To regenerate on cloud, run `tools/generate_setup_font.py --font PATH_TO_NotoSansCJK-Regular.ttc --output-dir NEW_SOURCE_DIR` with Pillow12.0.0; SC face index2 is checked. Update glyph coverage and native/real-LVGL layout checks whenever messages change.

This factory workflow does not migrate an existing legacy MAC, replace its server credentials, remove a family binding or reset history. The provisioner deliberately rejects legacy identity conflicts. Applying it to a currently bound unit requires a separately prepared migration/backup decision; do not erase its NVS merely to exercise first-time onboarding. Real platform credentials/version, device code generation, physical flashing and phone BLE acceptance remain distinct prerequisites.

The candidate checks CA chain, hostname and certificate dates. Factory path uses bounded SNTP before TLS and reports an error when time cannot be synchronized. Certificate-date checking is a global SDK option: the compiled legacy branch keeps its old routing but has no new SNTP initialization. Therefore this factory candidate must not be advertised as a verified update for already deployed legacy devices. Current deployed firmware is untouched.

The protocol fixture is synthetic and cross-checked against unmodified official Espressif Python. The framing adapter is a vendor transport patch; it changes no SRP, protobuf or AES-GCM bytes. Tests/builds cannot establish real iOS/Android BLE compatibility, credential persistence/reset behavior, wireless coexistence/audio performance, physical playback or production provisioning readiness.

The factory Waveshare layout preserves NVS0x9000/0x6000, otadata0xf000/0x2000, phy0x11000/0x1000; OTA slots become0x20000/0x370000 and0x390000/0x370000. Assets move to0x700000 (same6MiB capacity), storage to0xd00000 (same3MiB), ending exactly at16MiB. It consumes the former unused tail, with no partition overlap. Normal legacy partition source remains untouched. Preserve the candidate partition table and flashargs with its app/assets; mixing versions is invalid.

Manufacturing order matters: write the verified full firmware image first, then its matching private factory NVS image; the full merged image contains erased gap bytes and would erase an NVS image written earlier. Verify the unit MAC and board selection before any separately authorized physical step. No tool here flashes or generates real factory identities automatically.
