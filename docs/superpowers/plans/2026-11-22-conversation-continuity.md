# 对话连续性改造：从「逐轮请求」到「像真人聊天」

> **给执行者：** 三步顺序推进，每一步独立可发布、可回滚。第 1 步只改服务端提示词投影，不动连接、不动账本、不刷固件。第 2、3 步依赖设备 AEC，未取得实机结论前不进入生产。所有运行测试、依赖与正式服务只在云端。

**目标：** 让对话在「逻辑」和「体感」两个维度都接近真人：不重复、不越纠正越错、换手等待从 2.2s 降到 0.6s 出声。

**非目标：** 不追求把模型首包（约 1.2s）压到真人水平，物理下限不动；不替换千问原生 Realtime；不删除播放账本、回执与代次保护。

## 二、架构判断（为什么要改）

当前是「有状态的外壳 + 无状态的内核」：会话、账本、回执、所有权做得扎实；但对话本身每轮现场重建。

1. **上游会话逐轮新建**：`reply()` → `NewNative` → `Dial` → `session.update(全量提示词)` → `response.create`。模型每轮第一次见用户，连续性完全依赖提示词里的历史 JSON。
2. **两条连接、同一段音频**：监听连接做 VAD+ASR，回答连接只收本轮 PCM；转写靠 `currentTurnInput` 补进提示词。一个「听懂」、一个「回答」，两者可能理解不一致。
3. **上下文是带诊断的历史转储**：`ContextFor` 输出 16 轮、含 `playback_evidence`（`spoken_text`/`observed_text`/`tail_words` 等）与重复的助手正文。2026-11-14 评估已证明：错误回答被多次回灌后越纠正越重复，只删掉最近错误助手文字的全部副本即恢复话题（2/2），删数千字旧记忆反而无效。

### 第 1 步：对话状态对象——已上线

把回复用的上下文从「历史转储」换成「精简投影」，并显式给出「不要复述」。

- 新投影 `realtimestate.ConversationStateFor`：只保留 `id / user / assistant_spoken_prefix / position / interrupted`；8 轮上限；用户与助手文字各 512 字上限；不输出任何播放诊断结构。
- 反反复述不另建顶层字段：`assistant_spoken_prefix` 的开头就是「说过的开头」，规则写进提示词的 schema 说明。曾设计顶层 `said_openings`，实测发现内存清理只按 floor 过滤 `recent_turns`，顶层副本会在「清除记忆」后继续进入提示词（`TestMemorySelectionClearAndCancelInvalidateInFlight` 复现），因此取消该设计：投影里所有用户/助手文字只能存在于 turns 内部。
- `composeReplyPrompt` 增加精简 schema 说明；当轮转写仍必须是最后一行。
- `restored_context` 事件补 `context_chars`，用于上线后核对瘦身幅度。
- `ContextFor` 与身份/故事提示词常量**保持原样**：Python 差分测试逐字节比对，不能动。

预期：提示词从 4k–12k 字降到 1–2k，真实首包约省 150–400ms（估算，预填成本），**主要收益在逻辑而非延迟**。

验收：
- 单测覆盖「无诊断字段 / 长度上限 / 文字只存在于 turns 内 / 体积不大于原投影一半 / 提示词尾部顺序」。
- 云端 `go test -race ./...`、`go vet ./...`、`go build` 通过；Python 差分不受影响。
- 现场 4 条语料各 5 次：普通轮无 `music_plan`，回忆轮有 `memory_selection`；`context_chars` 中位数明显低于改造前。

回滚：单个提交 revert；无 schema、无固件、无部署形态变化。

### 第 2 步：抢话（先出声）——已实施，做法与原设计不同

原设计是「固定短语预合成 + 作为独立 turn 下发」。实施前否掉了这个做法，原因有两条：

- 独立 turn 意味着两条音频流之间做交接，那正好是历史上出爆破音的位置；
- 「要不要联网」在话尾那一刻并不知道，按意图预测必然漏掉纯上游卡顿（现场那次 8.1 秒的轮次答案只有 14 个字）。

改成**时间触发 + 同一条流**：话尾后 2.2s 仍无首包，就用一条极短会话生成一句安抚，写进本轮同一条音频流的前段；正文先到就整段丢弃。文案由模型组织，且**不许提「查」「搜」**（`cfg.Search` 是允许开关，不代表真在搜）。详见 `2026-11-22-preface-acknowledgement.md`，含两次现场返工的根因。

- 不新增 turn：账本、代次保护、600ms 播放信用窗口看到的仍是一条连续流，因此没有触碰红线。
- 验收改为：慢轮话尾→首声 ≤2.2s；正常轮不出现安抚；安抚句不得重复、不得声称查询。

#### 2b 的最终结论：预合成池下线，改成提示词内自组织开场（2026-11-23）

预合成池把阈值做到了 1.4s，音色、电平、抢占都验过，但它有一个绕不过去的性质：**能说的句子只有合成时切下来的那十几条**。第 N 次听到同一句「我想想啊」，它就不再是回应，而是录音。这不是文案不够多的问题，池子再大也会听出来，因为它不是对这一轮生成的。

改成让模型自己在正文流的第一句说：确实要检索或要想一下才铺垫，每次现想、不套固定句、说完立刻进正文、能直接答就不垫。约束写在 `realtimestate.OpeningGuidance`（A/B 链路的精简版在 `qwen.Instructions`）。

- 延迟不增加：不开第二个请求、不做第二次合成，铺垫就是本轮首包里的第一句。
- 音色天然同源：同一条流、同一个人，不存在 A/B 链路上池子与正文音色串人的问题。
- 代价：出声时机从「1.4s 必定开口」变成「不早于正文首包」——慢轮仍有 1.1–2.7s 的沉默，换取说的话是真的。
- 风险：模型可能判断不准该不该铺垫，或退化成「我这就查一下」式套话。靠提示词约束 + 现场连续追问同一件事三次来验。

#### 2c 的最终结论：提示词管不了「什么时候说」，改回服务端超时补偿（2026-11-23）

现场八轮实测（`20261123T041955`）推翻了这个做法。真正的搜索轮是第 3、4 轮，首包 3833 / 4602 ms：

- 第 3 轮（天气）**一个字铺垫都没有**，直接给 44 字答案。
- 第 4 轮（新电影）模型**确实写了铺垫**——`generated` 里是「我这就帮你找找最近上映的新电影。」，`spoken_text` 里也有；但词级时间戳显示第一个词「最近」从 160 ms 开始，18.06 s 的音频里没有这 1.4 s。也就是说：**文本写了、音频被搜索打断丢掉了**。
- 它选的说法本身正是被否掉的那类模板。

根因不在措辞：`enable_search` 是 provider 的内置插件，检索在模型出声之前跑完，模型根本没有可以说话的位置。提示词只能决定「说什么」，决定不了「什么时候能说」。

因此改回服务端补偿，但换掉触发方式与内容来源：

- **触发**：话尾 1.5 s 内没有首包才触发（从 `rt.stoppedAt` 算，不是从请求发出算）。实测正常轮 1.26–1.63 s，可能踩到；踩到了也没有代价。
- **放弃**：正文首包在任何时刻到达，立刻取消生成；若生成已完成而正文包已在队列里，直接丢弃，一个字都不播。
- **内容**：`rescueLine` 带本轮用户原话现写一句，不经任何预合成、不缓存、不轮换；`rescueAcceptable` 拒绝超 14 字、含问句、超 2.5 s 的输出——模型若开始答题，宁可静默。
- **音色**：同一个 `NewNative`、同一 voice（Tina）、同 24 k s16le，天然同一个人；A/B 链路不启用（它们用 longanyang，混进来就是两个人在说话）。
- **顺序**：补偿先播，正文排在它后面（最多等一条短句）。
- **指标**：`first_packet` 记用户听到的第一声（含补偿），`answer_first_packet` 记正文首包，两者分开才可跨版本比较；补偿内容另记 `rescue_line`（文本、采样数、话尾后毫秒）。
- **代价**：慢轮出声约 2.6 s，仍远于真人 0.2–0.5 s；剩下的差距在 provider 检索，要再压只能自己接管搜索（关插件、并行检索、二段回填），工期按周算，暂不做。

删掉 `realtimestate.OpeningGuidance` 与 `qwen.Instructions` 里的对应句：留着只会产出被吞掉的文本和套话，并让文本记录与音频对不上。

### 第 3 步：常驻单连接 + 设备 AEC——已证伪，不做（AEC 另行立项）

2026-11-22 三个探针推翻了这一步的收益假设（脚本在 `tools/`，均可重跑）：

| 测量 | 结果 |
| --- | --- |
| 常驻会话 10 轮 | TTFT 520 → 553ms（**+33ms**），`input_tokens` 713 → 1027 |
| 每轮新建会话 10 轮 | TTFT 中位 **590ms**，`input_tokens` 恒定 713 |
| 两者中位差 | **6ms**（常驻略快，在噪声内） |
| 提示长度成本 | 每 1000 token 约 **77ms**；生产约 3200 token ≈ 250ms |
| 音频输入 vs 文本输入 | **−23ms**，音频路径不额外花钱 |

结论：生产 1.1s 首包里，约 650ms 是模型基础延迟（物理下限），约 250ms 是提示预填，
剩余约 200ms 未定位（疑似音频时长）。**「省掉建连 150ms + 每轮重灌预填」这个收益假设不成立**——
常驻连接既没有收益，也没有出现担心的 TTFT 漂移。

因此本步取消。剩下的真实可砍项只有：提示词从 3200 token 精简到约 1000（≈170ms，
但会改人设，风险收益不匹配）与静音判定 600ms（≈150ms）。

AEC 仍然需要，但它解决的是「播放期间能不能听」，与首包延迟无关，应独立立项。

原设计保留如下，供日后条件变化时对照：

一条常驻会话承载听与说；Go 只做「何时允许开口 / 何时截断」的阀门与账本。设备侧评估 `esp_aec` SR 模式算力（现有 `firmware/probes/c3-aec` 仅供参照，目标板为微雪 S3）。

- 会话内只保留最近 3–5 轮原文，更早压进状态对象；每 20–30 轮或空闲 5 分钟重建一次。
- 落盘 `turn_index` 与首包耗时，监控 TTFT 漂移。
- 未取得 AEC 前，播放期间继续门控输入；第 3 步不得以「全双工」名义放开。

验收：真实首包 ≤0.9s；第 20 轮 TTFT 相对第 2 轮上浮 ≤20%；打断可 300ms 内截断且无爆音。

## 四、风险

| 风险 | 影响 | 处置 |
