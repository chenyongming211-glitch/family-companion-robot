# 2026-11-22 慢轮兜底播报（preface）

## 背景：实测数据

2026-11-22 现场两段会话（`20261122T075803` / `20261122T075948`）显示，话尾到首声在多数轮是
0.9–1.5s，但有三种慢轮：

| 类型 | 实测首包 | 起因 |
|---|---:|---|
| 联网搜索注入结果 | 6148ms / 2033ms | `input_tokens` 8036 / 9272，多出约 5k token |
| 记忆选择 | 2671ms / 2420ms | `memory_selection` 866–1056ms 串在前面 |
| 纯上游卡顿 | 8127ms | 无搜索、3580 token，答案只有 14 字 |

其中第三种无法在话尾预判，所以「按音乐/记忆那样的意图关键词门控」不能覆盖全部慢轮。

## 决策：时间触发，不是意图预测

话尾后 1.1s 仍无音频，就并行要一句安抚；正文在此之前到达则取消，一个字都不播。

- 正常轮 p50 1.09s，多数不会触发；触发率约三成，且其中一部分会在正文到达时取消。
- 覆盖三种慢轮，包括完全无法预判的上游卡顿。

安抚句本身要模型生成，实测（`/tmp/probe_preface.py`，文本输入 + 音频输出）：

- 建连 + `session.update`：76–140ms
- `response.create` 到首个音频包：541–626ms
- 输出示例：「我这就去查一下杭州明天的天气。」「我翻一下咱们的聊天记录。」

所以目标是**话尾后 2s 内出声**，不是 1.4s。对 6.1s 那轮，体感从 6 秒死寂变成 2 秒开口。

## 结构：同一条流的前 1.5 秒，不新增轮次

`reply()` 现在是一条 turn 一条连续 PCM 流，交给播放账本和 600ms 播放信用窗口。
把安抚拆成第二轮，等于在两条流之间做交接，正好踩在历史上出爆破音的位置。

做法：

1. 正文生成照常启动，写进 `encoded` 通道。
2. 话尾后 1.1s 若 `encoded` 还没有任何正文包，安抚 goroutine 抢到「前段权」，另起一条极短会话
   （无历史、无音频输入、`enable_search` 关闭、限 15 字），把自己的 PCM 写进**同一个** `encoded`。
3. `prefaceOrder` 令牌保证顺序：安抚持有令牌期间正文首包等待，安抚最后一个包发出后正文才入队；
   同一通道 FIFO，播放顺序即正确顺序。
4. 正文先出声 → `claim()` 失败，安抚不生成。
5. 用户插话 → 走现有打断，`rt.ctx` 取消，安抚一起停。
6. 音乐/媒体轮不启用：`media` 为真时不安抚，媒体本身就是即时输出。

所有对外的身份不变：同一个 `turn.ID`、同一个 `begin`/`end`、同一份账本和代次保护。

## 文案约束（诚实性）

**不许说「查」「搜」「翻资料」——任何情况下都不许。**

`cfg.Search` 是「本轮允许联网」的能力开关，现网每轮都是 true，它不代表这一轮真的会去搜。
按它来选措辞，等于每句安抚都在承诺一次搜索：问「你叫什么」也答「我这就去查查」。
真正知道自己在查什么的是正文，所以「查」这个动作只由正文自己说。

安抚只说一件事：我在，马上说。措辞由模型自己组织，且把**最近 4 句已经说过的原话**
作为「必须换一种完全不同说法」的清单一起传回去——「每次换个说法」是模型无法自审的规则，
一份具体清单才有效。

## 观测

- `preface`：`{id, fired_after_ms, outcome, search_enabled, text, samples, first_pcm_ms}`
  outcome ∈ `spoken` / `cancelled_by_answer` / `empty_input` / `error`
- `first_packet`：语义改为「用户听到的第一声」，包含安抚段，这是体感指标。
- `answer_first_packet`：正文自己的首包，保留与旧数据可比的口径。

## 验收

1. 慢轮话尾 → 首声 ≤2.2s（`first_packet.speech_stop_to_packet_ms`）。
2. 正常轮不受影响：p50 仍在 1.1s 内，`preface` 事件里 `cancelled_by_answer` 占多数。
3. 没有重复开场：正文自带开场白时不能出现「我查一下……我查了一下……」。
4. **微雪实机无爆破音、无双音**：安抚和正文是同一条流，理论上不触发拼接问题，
   但这条必须在真机上验，Mac 窗口验不出来。

## 回滚

`preface.go` 一个文件加 `reply()` 里的一处接线；把 `prefaceFireDelay` 置 0 或删掉 goroutine 即恢复原行为，不动账本。

## 现网反馈与修正（r2 → r3）

首轮现场测试只问了一句「你叫什么？」，结果：

- 听到的第一声是「我这就去查查。」——问名字不需要联网；
- `first_packet` 2544ms，比上一版同长度问题的 1.1s 还慢。

三条独立的错，叠在一起：

1. **话术被「查」锁死。** `searching` 取的是 `cfg.Search`（每轮 true 的允许开关），
   提示词于是告诉模型「你要联网查一下」。模型只能在「在查」这个前提下换说法，
   所以每种问法都落成同一类句子。这是「话术固定」的真正原因，不是模型在套模板。
2. **阈值落在正常轮中间。** 1100ms 就是上一版实测的 p50（1086ms），
   等于一半正常轮都会触发。安抚的成本是 0.6s 首包 + 一次请求，
   只有正文预计超过 2.2s 时才划算。
3. **触发即占住流首。** `claim()` 之后就 `acquire()`，正文首包必须等安抚整段写完，
   于是 1.5s 就能开口的正文被推到 2.5s。这是「加了安抚反而更慢」的机制。

修法对应三条：

- 阈值 1100 → **2200ms**：高于正常轮尾部，低于它要拯救的轮（2.7s 记忆 / 6.1s 搜索 / 8.1s 卡顿）。
- 文案彻底不许提查/搜；已说过的句子做成清单回传。
- **首包就绪才占位**：`begin()` 在第一个包到手时竞争，正文在此期间到达就直接赢，
  安抚整段丢弃（`cancelled_by_answer`）。不再有「安抚拖慢正文」这条路径。

验收追加一条：**问「你叫什么」「讲个故事」这类不需要新信息的问题，不应出现任何安抚**；
若出现，不许出现「查」「搜」。
