# 按设备选择音频传输格式

日期：2026-11-01（Asia/Shanghai）。用户已确认采用本方案并要求记录，作为后续终端音频开发的约定。

## 已确认的选择

| 终端 | 音频传输策略 | 采用条件与原因 |
|---|---|---|
| Xmini ESP32-C3 | 新方案采用原生 PCM | 先通过实际 CPU、内存、网络、声学与故障恢复验收，再替换稳定按键版；通过省去 Opus 编解码，为更完整的回声处理腾出资源。 |
| 微雪 ESP32-S3 Touch AMOLED 2.16 | 保留现有 Opus | S3 资源更充裕，继续保留压缩传输节省带宽的收益；不随 C3 的 PCM 成功自动迁移。 |
| M5 StopWatch ESP32-S3 | 保留现有 Opus | 继续使用既有音频路径；不随 C3 的 PCM 成功自动迁移。 |

这里约定的是设备与 Go 服务端之间的音频传输格式。设备内部采集、回声消除和播放仍处理 PCM；Go 服务端与千问实时语音之间继续使用 PCM。

## 共同服务端与格式协商

- PCM 和 Opus 复用同一套 Go Session、模型接入、设备鉴权与归属、近期记忆、设备工具和播放回报逻辑，不按终端另建整套业务服务。
- 设备在连接时显式声明固件支持的格式和能力，服务端校验后使用约定格式；不猜测音频格式，不在会话中自动切换或隐式回退。
- C3 PCM 使用 `version=1`、`format=pcm_s16le` 和 `pcm_s16le_v1` 能力；输入为单声道 16kHz/16bit/60ms，输出为单声道 24kHz/16bit/60ms。原有 Opus 终端兼容性必须保持。
- 共同的 VAD、取消和 drain 策略沿用现有设计；格式选择本身不代表自然插话已经验收。

## 后续迁移原则与当前边界

C3 的 PCM 成功，只证明该实现满足 C3 的验收要求，不作为其他设备改用 PCM 的依据。以后若考虑迁移微雪或 M5，须先在对应硬件上对照验证 CPU、内存、网络带宽、延迟、稳定性和声学效果，再单独决定；当前保留 Opus。

本次记录是方案确认，不是固件安装、正式部署或声学验收结果。C3 有界 PCM 的实施进度与资源/构建/安装门槛继续以[设计](2026-11-01-c3-bounded-pcm-design.md)、[执行计划](../plans/2026-11-01-c3-bounded-pcm.md)及后续验证报告为准。
