# 表情编排与可配置机器人名称：方案草案

日期：2026-11-08。

状态：用户已明确要求机器人名称不得硬编码，以支持未来客户自定义。三层表情分工沿用已采用的CHICK-01设计；模型情绪接入方式与以下生命周期调整仍是待评审建议。本文件不表示已经实现客户改名、情绪工具或自定义唤醒词，不新增模型调用、部署或刷机。

## 当前实现

- L0由设备/Go真实事件驱动，配中文状态文字；L1情绪与L2微动作不显示名称。
- 固件支持19个情绪串映射、参数化绘制、实际DMA幅度嘴型及本地微动作。Go已发送思考/聆听元数据，尚无自动模型情绪选择链路。
- `config/product-identity.json`已有`name`，模型身份通过Product读取；当前是启动时读取的产品级配置，尚非客户/设备级动态名称。
- 固件`chick_face_model.h`的启动、说话、提示文案仍有三处“小满”；`memoryClearCommand`也固定剥离“小满”称呼，均列入名称改造范围。

## 用户新增确定要求：名称配置化

1. 每台设备可以有客户设置的机器人名称，以稳定的设备身份读取；未设置时采用产品默认名称。“小满”可以作为配置值，业务代码、界面模板和提示词不绑定这个值。
2. 会话采用同一份设备名称配置快照；模型自称、身份介绍、情绪选择上下文及明确需要名称的展示统一读取，避免不同模块各自维护名称。客户改名通过设备配置入口更新，不将一般聊天或角色扮演自动写为永久名称。
3. L0优先采用“正在启动”“正在说话”“有新提示”等通用文案。需要出现名字的位置采用名称参数；长名称的排版/长度约束另行定义，不能让客户输入破坏状态提示。
4. 记忆清除等命令处理不能固定识别“小满”前缀；后续使用当前设备名称或名称无关的命令解析，同时保持既有删除意图/目标检查。
5. 名称仅作可变展示资料。设备ID、鉴权、客户归属、聊天记忆及声音身份不使用名称作主键；改名保持原设备的记忆归属，不影响其他客户设备。
6. 机器人称呼与离线唤醒词分别管理。当前微雪的声学命令仍为构建配置`xiao man`/“小满”；修改模型/屏幕名称不等于修改唤醒识别。客户配置必须能说明当前实际有效的唤醒词；动态唤醒词的加载、识别能力与验收另做方案，不能预先承诺任意名称均可离线唤醒。

## 表情分工与场景

设备决定正在做什么，模型选择回应态度，固件生成自然动作。L0保持实际采音/播放/电源依据，语音嘴型取实际DMA播放幅度；L1以平静、开心、喜爱、放松为日常主要表达，哭泣/生气优先用于明确剧情。聆听、思考及系统提示按既定优先级接管；L0文字不随情绪改成心情名称。

情绪选择接口建议为`set_expression({"emotion":"happy"})`，只允许已有情绪枚举；设备/会话/回复身份由系统提供。主语音会话内联合工具输出需要能力验证：当前`sessionSettings`配置工具后切文字模式，`Native.Open`也将搜索与工具分开。并行无声情绪分支符合现有适配结构，但每轮会增加模型调用成本，标签也可能晚到；该选择尚未进入实现。

首版建议每轮最多一个主情绪，绑定具体会话和播放回复。Go与固件共同校验身份，待实际播放相应回复才生效；旧音频排空时不提前应用新回复情绪。未开始的旧回复取消后丢弃待显示标签；旧尾音结束后清除其作用，避免旧情绪在下一轮重新出现。情绪缺失、未知、失败或过期时用neutral，语音播放不等待情绪结果。首段对齐和允许晚到的边界需要用实际流式输出确定。

当前固件有全局5秒上限，不能称为整轮保持。待评审建议：绑定回复的主情绪随该轮实际播放保持，播放结束后最多留2秒；独立的临时表情指令最多5秒。这个调整需要固件生命周期改造，尚未实现。

## 后续实施与验收范围

- 名称改造先覆盖模型身份、固件状态文案和现有称呼解析；设备配置存储/同步与生效边界需进入后续实施计划。
- 两台设备配置不同名称时模型自称相互隔离；重连/重启保持正确名称，改名不迁移记忆或改变设备身份。默认名称仍可在配置中设置。
- 分别验证有效唤醒词与展示名称，不用文字改名冒充声学改名通过。
- 情绪链路验收覆盖首包延迟、实际播放对齐、打断/排空/断连跨轮隔离及失败回退，不以接口存在代替实测。
