# 表情编排与可配置机器人名称：首版定稿 v1.0

日期：2026-11-08。

状态：本文件将此前草案收敛为作者定稿，首版技术选型、范围、协议、生效时序与验收规则均已固定，供用户审阅及后续实施计划使用。用户已明确要求三层表情分工、L0配文字、取消小光球，以及名称不得硬编码；本次任务仅定稿方案，未执行新增模型调用或新功能部署，不表示已实现情绪工具、客户改名或自定义唤醒词。

## 1. 目标和首版范围

保留已安装的CHICK-01资源、参数化渲染与实际DMA观察，完成如下交互：专注聆听→思考→带适当情绪说话且随实际声音张嘴→播完短暂保留表情→回到待机。插话排空、断连、错误和改名均有明确处理。

首版统一交付设备名称配置、模型情绪选择、Go回复绑定、固件按实际播放生效、情绪生命周期及联调验收。内部按模块实现，整条链路通过验收后交付完整版本。日常和剧情场景共用现有全部情绪预设，不为每种表情重建一套调用流程。

按句子切换多个情绪、音素级精细口型、翅膀电机、模型唤醒语音应答、任意自定义声学唤醒词属于后续独立功能。本版名称配置不声称改变当前离线唤醒命令，也不替代原唤醒可靠性和长期电源验收。

## 2. 已固定的技术选型

采用独立的无声情绪选择分支，与现有主语音生成并行。两者使用各自的连接和不可变配置副本。主语音继续原生音频与现有联网搜索；情绪分支关闭搜索、只输出结构化工具结果，不产生播放音频。不得将情绪工具直接追加到当前主语音Tools配置：当前适配器配置Tools会切文字模式，且Native.Open将工具与搜索分开。

这是首版确定选型，不在开发中继续并列主会话工具/独立分支/关键词三种路线。未来若验证了主语音与结构化情绪联合输出的能力，可另立版本替换选择器，沿用本版的回复绑定与显示协议。

代价明确：每个具备新表情能力、仍有效且需要语音回复的用户轮次，最多增加一次情绪模型生成请求；会话握手也消耗连接资源。没有该能力的旧终端、启动/健康检查、纯设备握手不触发调用。情绪分支超时或失败不重试，不启动补救模型调用，不让主语音等待。

## 3. 三层职责和优先级

| 层级 | 内容 | 决定方 | 文字 |
| --- | --- | --- | --- |
| L0 | 启动、配网、连接、待机、采音准备、聆听、处理回复、说话、排空、通知、异常、升级、电源 | 设备与Go真实事件 | 显示实际状态或具体提示 |
| L1 | 当前回复的表达态度 | 模型选择，Go和固件核验 | 不显示情绪名称 |
| L2 | 眨眼、呼吸、视线、小动作 | 固件本地定时与已有动画模型 | 无标签 |
| 说话嘴型 | 实际播放声音的幅度 | 当前连接/播放身份的实际DMA观察 | 不另加字幕 |

预览和原系统页面继续拥有显示权限，异常/升级保留高优先级。聆听与思考采用对应L0表现；实际说话时眉眼可表达L1，嘴巴由实际输出驱动。后台新回复开始生成，不能提前覆盖旧尾音的表情。省电只降低亮度和动画频率，息屏停止UI，不自动切sleepy。

## 4. 情绪选择接口、输入和场景

内部工具固定为`set_expression({"emotion":"happy"})`。参数只有emotion，不允许模型指定设备、会话、回复ID、文字、亮度、任意绘图参数或寿命。系统提供身份与时间信息。

工具使用15个规范值：neutral、happy、loving、embarrassed、confident、delicious、sad、crying、sleepy、silly、angry、surprised、winking、relaxed、confused。固件保留已有19字符串兼容映射；模型入口采用规范值，thinking由真实L0生成状态表示。

| 回应场景 | 选用方向 |
| --- | --- |
| 普通问答、表达不明确 | neutral |
| 分享好消息、祝贺、鼓励 | happy |
| 关心、感谢、亲近 | loving |
| 被夸奖 | embarrassed或happy |
| 鼓劲、挑战、自信讲解 | confident |
| 轻松陪伴、放松引导 | relaxed |
| 需要澄清意思 | confused |
| 有趣的意外转折 | surprised |
| 美食、食物剧情 | delicious |
| 笑话、游戏、俏皮剧情 | silly或winking |
| 悲伤剧情、温和共情 | sad |
| 睡前告别、角色犯困 | sleepy |
| 明确剧情或角色扮演 | 可按情节使用crying、angry |

表达的是机器人准备采用的回应态度，不是用户情绪的确定识别。日常以平静、开心、喜爱、放松为主；受到批评时保持温和认真。只有用户原话和有限已播背景可作依据，不将引文或旧助手身份当成配置修改指令。

当本轮转写和已播上下文可用时启动一次选择，输入包含本轮用户原话、当前机器人名称和与主语音一致的有限已播背景。首版选择总体回应态度，不等待整段助手稿，不逐句重选；若选择启动前已有本轮助手文字，可加入已有前缀，禁止为等它阻塞语音。情绪与实际回复的语义一致性列入真实模型场景验收，不能宣称单靠接口保证一致。

从情绪调用启动到结果接受的总时限初值为2000ms，包括建连和推理，受本轮取消上下文约束；只接受一次完成的合法工具结果。缺失、非法、多个冲突工具调用或超时均回neutral。2000ms是首版工程上限，不是已验证的最优值；调整必须版本化并保留测量依据。

## 5. 回复绑定与协议

新增可选能力`face_expression_v1`，与现有`face_state_v1`分开协商。只有新固件声明该能力后，Go才下发表情。旧固件不能因为能接收普通emotion字段就被视为已实现跨轮隔离。

Go将选择结果保存到当前回复，持有会话、连接和播放ID。模型不能提供这些ID。Go发送消息前，在既有会话串行写入范围核验回复身份、未取消、未实际播放终结和当前输出归属；模型生成结束或tts.stop本身不代表实际播放终结。

消息沿用llm类型，固定增加播放身份：

```json
{
  "type": "llm",
  "session_id": "当前已鉴权会话",
  "playback_id": 17,
  "emotion": "happy"
}
```

若标签已准备好，发送顺序为有效tts.start、情绪元数据、首段音频；不会为了等标签推迟tts.start或首段音频。尚未开始的回复只在Go持有标签，不向设备发布悬空播放ID。标签稍后到达时，最多发送一次，并再次核验当前回复仍有效。

固件接收时在现有协议锁下同时核验会话、连接代次、已开始的播放ID及合法情绪，取得不可变事件；主任务应用前再核验，防止排队期间断连/换轮。用有界存储保存待应用标签，容量沿用已有播放记录上限，不保存PCM，也不新增音频路径锁。

收到标签不代表立刻换脸。当前实际DMA播放身份匹配时才应用；未匹配时保持待应用状态。每轮最多应用一个主情绪。主语音不等待标签：未到时保持默认表情；允许在该回复实际首个有效DMA完成后的2000ms内补上一次，超过窗口或实际播放已经结束则丢弃。窗口由固件实际播放时钟判断，不用服务端下发时刻冒充播放开始。为此扩展已有观察快照的必要起止时间标量，在原有DMA完成记录与锁范围内发布；UI读取快照，ISR不绘图、不计算PCM能量，不增加音频路径锁。

## 6. 生命周期与打断

| 情况 | 确定行为 |
| --- | --- |
| 标签早于实际播放 | 等待同一播放ID首次实际输出，再开始显示寿命 |
| 标签在开播后2000ms窗口内到达 | 当前仍在播放时应用一次 |
| 长回复持续播放 | 保持该回复主情绪，嘴型继续跟随实际幅度 |
| 正常实际播放结束 | 最多保留2秒，再回平静待机；新状态可提前接管 |
| 旧生成取消且还未播放 | 取消情绪调用，丢弃排队/未显示标签 |
| 已收到的旧声音继续排空 | 已显示旧情绪随旧声音保留；不再接受该旧回复的新标签，不提前显示新回复情绪 |
| 旧尾音结束，恢复聆听 | 清除旧作用；后续回复不得复活旧情绪 |
| 错误、断连、连接替换、系统页面接管 | 退回真实L0/系统页面，旧事件失效，停止相应待应用状态 |
| 未绑定播放的临时情绪 | 沿用独立事件最多5秒上限，不在首版额外开放新的客户控制入口 |

绑定回复的情绪采用本表寿命，替代当前统一5秒上限。旧的无绑定接口继续保持5秒保护。若屏幕被隐藏/关闭，按实际播放结束时间计算余留；恢复显示时不得重新计时或复活过期表情。

## 7. 可配置名称

名称按稳定设备ID读取，未配置时继承产品默认name。“小满”允许存在于默认配置、真实唤醒词及历史测试资料中，业务逻辑、状态文案、模型提示模板不绑定这个默认值。内部文件/类/目标名不是客户称呼，不做无关的大范围重命名。

首版新增独立的设备资料存储，不修改鉴权注册表：云端版本化JSON保存device_id对应的name与revision，通过云端管理命令读写、校验及原子持久化。服务为新会话读取最新有效资料，并生成不可变身份快照；当前通话保持原快照，改名在下一次新会话生效，无需重启整个服务。首版交付这个配置能力和管理命令，客户自助页面后续复用相同配置接口。

名称去首尾空白后须为1至12个Unicode字符、有效UTF-8，拒绝控制符和换行；作为JSON资料引用，不拼成模型指令。资料读取异常使用上次有效配置，首次无有效配置采用产品默认并记录原因；不因展示资料故障中断语音。

模型自称、身份介绍、情绪选择输入和需要名称的显示读取同一份设备资料。L0固定采用“正在启动”“正在说话”“有新提示”等名称无关文案；已安装固件的三处“小满”状态文字在本版移除。清记忆等命令剥离当前会话配置名称，不固定识别“小满”，并保留原有删除意图与目标检查。

改名不改变设备ID、鉴权、客户归属、聊天记忆或声音身份，不重写历史对话原文。身份提示明确历史名称属于当时称呼，当前正式名称以本会话快照为准。两个设备名称分别配置，不互相覆盖。普通聊天或角色扮演不自动永久改名。

称呼和离线唤醒词分别管理：当前微雪实际命令仍为构建配置xiao man/“小满”。配置读取/管理结果说明已核实的当前有效唤醒词；没有可靠固件能力记录或设备回读时明确返回unknown，不从名称推断。不能把显示名更新记成声学切换成功。动态唤醒词另行设计和验收。

## 8. 验收与交付门槛

1. **工程逻辑：** Go普通/race、vet/build；固件生产方法host/sanitizer及五目标构建。覆盖15规范值、旧映射兼容、协议协商、非法/旧会话/旧ID拒绝、重复、超时、并发取消、排空、跨连接和界面隐藏恢复。
2. **时序：** 使用实际播放ID和DMA事件证明早到等待、晚到窗口、长回复保持、播完2秒回落。L0文字真实，L1/L2无名称标签；情绪不能推动或伪造音频进度。
3. **名称：** 两个设备配置不同名称，重连/重启保持；活动通话快照稳定、新会话采用改名；清记忆仍遵循原意图检查，记忆/鉴权归属不随改名变化，默认名称只在配置层决定。
4. **真实模型：** 运行前固定20个场景及每例可接受情绪集合，覆盖日常、中性、祝贺、澄清、陪伴、剧情、长回复与干扰。正常场景要求在约定时限内得到可接受情绪并在有效播放窗口内生效；另设可控故障用例验证neutral回退。全部预注册必测用例通过才交付，正常场景超时不自动算通过。报告合法输出、完成耗时、语义一致性、实际生效率、超时/过期/默认比例和token用量，不把neutral回退记成成功显示目标情绪。语义不一致或首段对齐失败如实留档，不能只凭JSON合法宣称自然互动通过。
5. **语音和资源：** 同场景按分支开/关交替记录首包时延分布、音频完整性、打断排空、CPU/内存和表情帧开销。音频不得等待情绪结果，现有设备窗口/格式策略保持。模型新增调用次数每轮不超过1，不计协议握手为额外生成但须记录连接成本。
6. **实机：** 自动化完成大部分状态与异常验证，现场用最少自然交互确认正常问答、祝贺及一次插话；不能以合成/host结果替代真人视觉和声学观察。失败则修复并复验，不以“已写接口”交付。

下一步只制定对应实施计划，然后分模块开发和审查，最终统一联验与交付；本文件不启动运行时改造。已安装版本、原测试与未验项目继续见[CHICK-01验证记录](../../verification/2026-11-08-chick-face.md)。
