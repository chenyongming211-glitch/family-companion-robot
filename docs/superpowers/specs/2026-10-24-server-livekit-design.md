# 服务器端LiveKit链式语音：架构细化

2026-10-24。用户已确认采用服务器端LiveKit＋ASR→LLM→TTS的方向。本文件落实接入边界与验收顺序，不重新选择框架。本轮仅细化方案，未部署新服务或切换手表。

## 1. 已确定的目标

唤醒一次→连续对话、随时插话→空闲超时待机。故事中断后先回答旁支问题，用户说“继续”时从首个未完整播完的句子继续，保留原稿；数数按最后完整数字继续并保留原终点。重复插话使用最新检查点。正常流程不要求用户报告起点。

保留原请求、对话记录、放弃/清空、重启恢复和设备音量/亮度控制。首版一台M5StopWatch、一个活动会话，不增加摄像头、人格系统、向量库或多任务栈。

## 2. 首版拓扑和责任

```text
M5StopWatch（现有固件、AEC、唤醒、I2S回报）
  ↕ 小智WebSocket，Opus
Go设备接入层（鉴权/OTA/编解码/播放身份/MCP）
  ↕ 同机受保护WebSocket，PCM＋有身份的控制/回报
Python运行时：LiveKit Agents＋自定义AudioInput/AudioOutput
  ↕ 模型插件或薄协议适配器
流式ASR → 文本LLM → 流式TTS（先调用云API）
  ↕
本设备任务检查点与文字快照
```

这里的“服务器端”是运行在现有云服务器上，不依赖Mac常开。**LiveKit Agents是首版语音底座；独立LiveKit Server/SFU媒体服务暂不作为必需项。** 当前手表已经使用WebSocket，可直接接Agents自定义I/O，减少一次媒体编解码和播放时钟；将来确有WebRTC客户端需求再引入房间/媒体服务。本选择须先通过第一阶段真实SDK契约验证，不能仅凭文档宣布集成成功。

固定源码`7a7547e442aaf9cf6f6cab54dd5db6f7cfb5a964`的`AgentSession.start`允许不提供room，已设置的音频输入/输出可替代RoomIO。`AudioOutput`提供播放完成/进度回调。参考：[会话源码](https://github.com/livekit/agents/blob/7a7547e442aaf9cf6f6cab54dd5db6f7cfb5a964/livekit-agents/livekit/agents/voice/agent_session.py)、[音频I/O源码](https://github.com/livekit/agents/blob/7a7547e442aaf9cf6f6cab54dd5db6f7cfb5a964/livekit-agents/livekit/agents/voice/io.py)。这是源码能力核对，不是本项目新链路实测。

| 组件 | 负责 | 不承担的职责 |
|---|---|---|
| 手表 | 唤醒、采集、AEC、扬声器输出、已有播放回报 | 模型API、任务稿持久化 |
| Go接入层 | 鉴权、OTA、小智协议、16k上行解码、24k/60ms下行编码、单写者播放ID、MCP设备工具 | 新后端不再调用原生千问、另做VAD/路由/生成编排 |
| LiveKit Agents | 会话、VAD/端点检测、取消、模型管线、工具调用和当前ChatContext | 把主机发送量直接当手表播放量 |
| 自定义音频I/O | 传递音频、保持播放身份，将有效设备证据接入SDK播放事件 | 根据语速估计、网络写出或入队推断已播文字 |
| 任务/记录层 | 原稿、原终点、完成前缀、版本、清空/放弃及有界文字恢复 | 不复制完整语音编排引擎，不把未播全文注入已说历史 |

Go现有原生后端保留为回退；新路径必须有自己的会话对象，不把LiveKit事件伪装成Qwen事件以继续运行旧编排。每个设备连接只运行一个语音后端，不双发音频/重复调用模型。迁移由边界适配推进，不直接重写整个`session.go`。

## 3. 模型与账号候选

| 环节 | 第一候选 | 首次实际调用必须核对 |
|---|---|---|
| 用户输入ASR | 百炼`fun-asr-realtime`，16kHz单声道PCM | 现有Key/业务空间/地域权限、完整与中间结果、取消/断开、错误回执 |
| 文本LLM | 百炼OpenAI兼容文本接口；`qwen-plus`作为候选别名，实际可用ID经探针固定 | 流式正文、工具调用、取消、上下文、推理模式开关和usage |
| TTS | `qwen3-tts-flash-realtime`，24kHz PCM；具体音色按可用列表选择 | 手动提交、首包、终态、词/句时间信息是否真实提供、取消、音色/费用 |

这些是候选，不宣称现有实时语音Key已获所有权限；URL分别配置，不能机械替换模型名复用同一个端点。SDK有同名Qwen模型也不代表它调用百炼托管端点。文本LLM优先复用官方兼容插件，ASR/TTS仅在确无适合当前协议的插件时写薄适配器，不修改LiveKit核心。首轮不新增供应商账号；权限不足时记录具体失败环节，再向用户索取该权限。

此处ASR识别用户输入，是链式语音的必要部分；此前讨论的“识别机器人输出以推断断点”的辅助ASR仍不在首版范围。不能用输入ASR时间戳代表机器人播放位置。

官方依据：[Fun-ASR客户端事件](https://help.aliyun.com/zh/model-studio/fun-asr-client-events)、[百炼兼容文本接口](https://help.aliyun.com/zh/model-studio/qwen-api-via-openai-chat-completions/)、[Qwen实时TTS](https://help.aliyun.com/zh/model-studio/interactive-process-of-qwen-tts-realtime-synthesis)。账号权限、音色、延迟和费用以实际探针为准。

## 4. 音频与身份契约

- 手表上行沿用16kHz单声道Opus，Go解码后以20ms PCM单位送入AudioInput；下行要求24kHz单声道PCM，由Go按现有1440采样/60ms编码。SDK/供应商若返回其他采样率，使用明确、有状态的重采样并纳入坐标测试，不能每小块独立四舍五入累积误差。
- 控制事件至少携带协议版本、device_session、input_epoch或output_epoch、segment_id和单调序号。Go分配实际playback_id并先确认绑定，再接受该身份的PCM。旧连接/代次事件直接拒绝，不能把到达时间作为归属。
- 音频和控制有界队列分开处理；队列满时关闭/报告故障，不静默丢语音。取消必须立即作废输出代次、清理待播队列；音频拥塞不得令取消等待预取或磁盘。每层均记录不含正文的计数/耗时。
- `capture_frame`、TTS生成终态、SDK音频输入结束、Go成功下发均不代表设备播放完成。AudioOutput的flush只封口；收到同身份有效设备最终回报后才报告完整播放。中断先停播，最终前缀有限结算；无效/超时不能升级为完整交付。
- SDK播放事件缺少“未知”数值时，适配器单独保留valid/unknown状态。为解锁SDK生命周期而提交的保守下界不能被任务层当精确测量或已播正文；这一失败路径须独立测试。
- 一条回复可以有多个TTS合成段；SDK flush、内容单位和固件tts stop不是必然同一个边界。须先验证这三个层次的归属，不让每句tts stop造成自动listen.start和错误新输入。

## 5. 对话、任务和持久化

所有正常问答使用同一LiveKit链式后端。故事/数数在其中使用内容任务：固定原稿、编号单位、已确认完整前缀及内容版本。优先评估TTS直接给出的可靠时间表；没有时间表时用已知短单位。数数无需强制每个数字一次远程请求，但任何数字完成都必须有可验证的音频边界。

两层职责、六项任务职责、Eino适用位置、最小数据与跨层接口见[实时语音与任务接续细化](2026-10-24-livekit-task-continuation-design.md)。实时语音由LiveKit Agents统一控制；Go任务模块持有原稿和播放事实。首个闭环复用现有任务/存储逻辑，Eino为可替换的编排实现，暂不作为必需依赖。

插话由AgentSession中断/取消机制驱动，设备AEC和真实播放状态参与适配；普通短中文插话、复述机器人用词、低声插话都要验证，不照抄OpenDeskBot的1秒时长或响度阈值。一次误触发恢复与真正旁支结束后的任务恢复分别测试。

旁支回答不改原稿/终点或主任务游标。“继续”读取同一任务的最新revision，重播当前未完成句/数字，然后播放剩余原稿。晚到final不能覆盖新播放代次。最后单位有效完成后才进入completed；放弃/替换/清空都使旧任务不可执行。

沿用文字快照7天、128条消息、单条512字符、恢复背景最多12条的边界；固定稿另有4096字符/128单位的有界任务数据，仍服从现有快照1MiB总限制。服务重启后恢复成功保存的检查点，未落盘的进度允许保守重读，不允许跳过。影子测试从空的独立数据目录开始，不复制真实正文；正式记录继续由单一Go存储owner管理，新旧后端任务状态须带engine/schema标记。正式切换前完成读写兼容与清空/放弃权威标记的跨后端测试；回退只能恢复兼容背景，不得复活旧任务或已删除正文。不能通过另存一份真实记录绕过清空；备份也受同一删除/保留策略约束。

新链路清空操作必须同时清理ChatContext、任务状态、持久化正文并取消在途模型/TTS/工具；不能只删除文件。手表工具复用`internal/devicetools`的白名单、回执和状态复核，模型不得绕过Go调用固件工具。

**显式关闭SDK录制。** 启动AgentSession设置`record=False`，不配置音频/全文trace recorder；ASR音频、原生回复PCM仅作实时有界内存处理。正文只经获准的文字存储写入，不混入日志。供应商留存另按供应商政策，不把本地关闭录制描述成云端零留存。

## 6. 仓库与部署边界

后续实现采用`services/livekit-agent/`放Python运行时/适配器，`internal/devicebridge/`放Go内网协议客户端，`internal/gateway/`增加一次性选后端分派；不创建第二套设备鉴权或OTA。独立审计工具放`tools/livekit-audit/`。本轮只创建方案文档。

首阶段SDK基线使用已有测试过的`livekit-agents==1.8.8`、RTC SDK`livekit==1.1.21`、Python3.12，固定源码7a7547e；解析并锁定完整依赖后再实现插件，不跟随main自动更新。若以后启用独立媒体服务，本次核对的稳定候选为LiveKit Server v1.13.10，仍需另行同组合验证，不能认为SDK与Server版本号相同。[Server版本](https://github.com/livekit/livekit/releases/tag/v1.13.10)。

现有8000端口保持原服务。新完整链路先在loopback测试端口和独立记录目录运行；对真实设备只在空闲/计划切换时启用明确的设备后端选择，旧连接保持原后端直到结束。Go设备Token、内网服务凭证、模型Key分开；内部端点仅loopback且鉴权，不让手表接触模型Key。第一阶段不改云安全组、不新增公网端口、不刷机。

main直接提交/推送，不创建分支或worktree；凭据、设备备份、用户音频、依赖环境和上游源码不进入Git。旧代码/旧发布保留回退；回退不能让新引擎继续处理同一设备输入。

## 7. 阶段与验收

| 阶段 | 出口 | 证据边界 |
|---|---|---|
| P0：SDK与账号能力 | 证明自定义I/O可接真实回报语义；查明三类模型实际端点/权限/时间戳能力；冻结依赖和接口 | 此阶段计划先落实SDK契约探针；模型调用需单独记录实际结果，不用文档代替 |
| P1：完整链式语音 | 合成输入经ASR→LLM→TTS→模拟设备；连续问答/取消/工具与记录通过 | 不是手表现场听感；不以此宣布准确接续 |
| P2：手表普通对话 | 唤醒、完整回复、音量/亮度、插话停声、连续收音和空闲待机 | 同一设备/音量80对照旧后端；记录误停/漏收音 |
| P3：自动接续 | 故事10轮、1～50数数10轮，覆盖再插话、边界和重启；不漏内容、不越终点，正常不询问起点 | 有独立听辨与设备坐标证据；句中打断允许重读当前句 |
| P4：正式切换 | 完整检查、资源/费用/延迟数据、现场验收和回退演练通过 | 每次只切一个设备会话，健康检查和源码/二进制/依赖身份一致 |

延迟统一分别记录：用户说完→ASR final、ASR final→首个模型正文、首个正文→首个TTS PCM、首个PCM→设备首播、近端语音开始→最后旧声音。不能把模型cancel回执延迟称为手表停声延迟。

初步体验目标沿用：已缓存接续在“继续”的完整转写确认后1.5秒内出声；预取正常时额外段间停顿p95≤250ms。它们是目标，不是SDK保证。若无已缓存语音或网络异常，分别报告；首句延迟和实际费用与原生后端同条件比较后确定上线取舍。现有服务器不跑云端大模型权重，先测CPU/内存再决定是否扩容。

## 8. 对旧方案的取代关系

本方案取代2026-10-23提案中“普通问答保留千问原生、仅长内容另接TTS”的主链路选择；保留固定原稿、真实播放检查点和验收场景。旧方案/实验仅作历史与回退依据，不再作为下一阶段默认实施路线。

首个可执行任务见[LiveKit接入第一阶段计划](../plans/2026-10-24-livekit-stage-zero.md)。P0结果出来后再逐阶段编写生产代码实施计划，避免提前根据尚未验证的模型权限和SDK回调写一整套迁移代码。
