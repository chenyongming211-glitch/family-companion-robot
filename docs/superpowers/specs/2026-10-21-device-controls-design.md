# StopWatch 音量、屏幕控制与杂音排查：最小修复方案

状态：已按确认方案实现并部署；音量/亮度/息屏控制与亮度语音确认已实机验证。呲呲声暂未复现，未宣称彻底消除。

## 已确认的问题

当前 Go 网关忽略设备 MCP 消息，千问会话未注册设备工具。视频中模型说“已经调大了”，但没有对应硬件执行链路。小智 v2.5.2 提供设备状态、扬声器音量、屏幕亮度工具，可沿用现有固件接入。

视频还报告偶发呲呲声。其根因尚未确认，须单独比较原始下行音频、网关 Opus 解码与设备播放表现，不能把它直接归因于 MCP 或回声消除。

## 修复范围与方案选择

采用千问原生 Function Calling → Go 网关 → 小智设备 MCP 的方式。另两种做法是仅用中文关键词匹配控制（表达范围有限）和重写设备固件（当前没有必要证据）。本次选择沿用固件，补齐服务端控制链路。

仅开放设备状态读取、音量 0—100、屏幕亮度 0—100。用户说“息屏/关闭屏幕”时设置亮度为 0；这不承诺设备关机或面板断电。相对音量调整先读设备状态。暂不接入任意 MCP、家庭自动化、固件升级或重启工具。

网关完成 MCP initialize 和工具发现后，才向千问注册实际可用的固定工具映射；不把任意设备描述作为系统指令。请求使用独立 ID 关联，参数必须是合法整数且在范围内。工具结果、错误和超时回传给千问，再继续回复；要求模型依据执行结果作确认，失败时明确说明未完成，避免无执行依据的“已经调好了”。设置后读取设备状态核对目标值，状态不可确认时不报告已核实。

保持现有语音协议与单设备限制。工具请求不阻塞音频事件循环；打断或上游重建后忽略旧一轮的迟到工具续答，避免旧结果触发新一轮语音。设备断线清理请求，不自动重试设置操作。工具发现和调用失败不泄露鉴权或上游原始错误。

## 杂音诊断与修复边界

先保留用户原视频，提取帧与音轨分析。核对下行 PCM/Opus 的峰值、截断和帧间隔；若确认网关按 `now + 60ms` 推迟下一帧造成累计发送漂移，则先写失败回归，再改为基于既定播放时间推进，避免每帧累积调度误差。是否增加预缓冲、调整音量或修改固件，要以实际证据为依据，不同时尝试多种修复。

## 验收

- 回归覆盖：MCP 发现、请求关联、参数范围、超时/失败、迟到结果，以及工具输出回传与续答顺序。
- 接入真实千问和真实手表，验证设置音量、相对调节、亮度和息屏，再读取状态核实；测试后还原原音量和亮度。
- 音频相关修改必须有能在旧实现失败的节奏或数据回归；修复后比较原音频、网关音频和设备现场表现。没有现场听感证据时不标为杂音已消除。
- Linux/macOS 按变更运行必要的测试、race、vet 和构建；按发布目录部署并保留回退版本。
