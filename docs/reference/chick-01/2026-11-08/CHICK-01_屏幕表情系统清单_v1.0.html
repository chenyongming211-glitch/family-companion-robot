CHICK-01 · Screen Expression Spec

屏幕表情系统清单小鸡翅膀款 · v1.0

屏幕 2.8″ 240×320 IPS（竖屏）
预设数 27 个表情 + 5 类微动画
实现方式 1 个参数化脸引擎（非序列帧）
依据 DeviceState 12 态 + 19 个协议情绪串

一、结论先行：不是「画 27 张脸」，是「一套参数 + 27 组数值」

这份清单把你项目里已有的两条真实约束对齐了：固件的 DeviceState（12 个状态）和协议里的情绪字符串（19 个）。表情不是装饰，它是这套会话状态机的可见输出。

层级来源内容数量
L0 状态DeviceState 状态机开机、配网、连接、待机、聆听、思考、说话、提示、错误、升级、低电、充电12
L1 情绪LLM 情绪串（协议）19 个情绪串收敛成 15 个预设，不新增协议字段15
L2 微动常驻叠加层眨眼、呼吸、视线游移、口型、待机小动作5 类
合计视觉预设27 个
为什么要分层：L0 决定「它在干什么」，L1 决定「它什么心情」，L2 让画面不像静止图片。三层叠加后，27 个预设能组合出接近 200 种观感，但代码里只有一张脸。

二、L0 系统状态表情（12 个 · 必做）

这 12 个直接对应 device_state.h 里的枚举，由状态机回调驱动，不依赖云端。下面每个都是 240×320 的实际效果预览。

背景为屏幕色，非实体颜色预览按 240×320 等比缩放
两个容易漏掉的：「升级中」和「低电」在状态机里没有独立状态（OTA 是 kDeviceStateUpgrading，低电要靠电源管理回调），但它们是最需要被看见的状态——用户不知道设备为什么不动时，脸是他唯一的解释。

三、L1 情绪表情（19 个情绪串 → 15 个预设 · 零协议改动）

下面这张表是从固件里读出的真实词表（emoji_display.cc 的 emotion_map），不是我自己编的。你项目现在链路里情绪只下发过 neutral，所以这 19 个是「已经支持但还没被用起来」的能力。

关键：19 个串收敛成 15 个预设，happy/laughing/funny 共用一套，「sad/crying」共用一套（crying 加泪层）。这样固件里只需要一张 emotion → preset 的映射表，未知情绪自动回落 neutral，永远不会因为云端下发新词而黑屏。

四、L2 微动画（5 类 · 叠加在任意表情上）

没有这一层，脸就是一张贴纸。这五项的成本很低，但「像活的」和「像图片」的差别几乎全在这里。

微动画触发参数帧率
眨眼随机 3–6 秒闭合 60ms → 保持 20ms → 睁开 80ms；10% 概率连眨两下15fps
呼吸常驻整脸 scale 1.000 ↔ 1.015，正弦 4 秒；说话时幅度降到 0.5 倍15fps
视线游移仅 idle2–8 秒随机一次，瞳孔偏移 ±12px，80ms 到位（模拟眼跳，不能线性移动）15fps
口型播放音频时嘴的张开高度 = 音频 RMS 包络，每 20ms 更新一次，带 60ms 平滑30fps
待机小动作30–90 秒随机歪头 6°、轻打哈欠（眼闭 400ms + 张嘴）、被叫名字时耳朵一抖15fps
视线游移那条最容易被做错：瞳孔要「跳」不要「滑」。线性移动看起来像机器人扫视，80ms 内瞬移到位才像眼睛。

五、和你项目状态机的对接关系

我把 device_state_machine.cc 里的合法迁移读了一遍，表情必须遵守同一套规则，否则会出现「界面显示在听，实际已经断开」这种撕裂。

迁移表情动作要点
Idle → Listening平静 → 聆听不要瞬间切换。先 150ms 交叉淡化，再睁大眼睛——硬切会像闪屏
Listening → Speaking聆听 → 保持情绪 + 开口型这里最容易出错：不是「切到说话表情」，是「情绪不变，只解锁嘴」
Speaking → Listening（被打断）惊讶闪 250ms → 聆听符合全双工直觉：被打断先微微吃惊，再听你说
Speaking → Idle嘴闭合 → 保持情绪 2s → 回平静话说完不要立刻变脸，留 2 秒余韵，情绪才有温度
* → Notifying眉毛上挑 + 感叹号提示必须和「说话」在视觉上区分开，否则用户以为在自言自语
* → FatalError下垂 + 皱眉 + 红色调不可逆状态，表情也不该再恢复

六、实现决策：为什么必须是参数化，不能用序列帧

这一步算错，后面全部要推倒。你项目里 emote_display 用的是 .aaf 序列帧资源（esp-hi 那套是 128×128 的），CHICK-01 是 240×320，面积大 6 倍，直接套用会炸。

方案Flash 占用CPU结论
序列帧（RGB565 全帧）27 表情 × 2s × 15fps × 150KB
≈ 120MB		低❌ 物理上不可能
序列帧（RLE 压缩）≈ 8–12MB中（需实时解压）⚠️ 吃掉 16MB Flash 的大半，且改一个表情就要重导资源
参数化绘制 ✅≈ 0（纯代码 ~15KB）4–8%（240×320，LVGL）✅ 推荐
参数化的额外收益：①改表情只需改数值，不用重导素材；②表情之间可以插值过渡（序列帧做不到）；③微雪 480×480 和小鸡 240×320 共用同一套参数（按屏宽归一化），换屏不用重做；④口型可以直接驱动「嘴张开度」这一个参数。

七、口型同步的接入点（你代码里现成的位置）

这是整份清单里唯一需要碰音频路径的地方，而且只需要 3 行。位置在 audio_service.cc 的 AudioOutputTask：

// main/audio/audio_service.cc · AudioOutputTask()
// 现有最后一行：
codec_->OutputData(task.pcm);

// 加在这两行之间即可（不改变任何播放行为）：
int16_t peak = 0;
for (size_t i = 0; i < task.pcm.size(); ++i)
    peak = std::max(peak, (int16_t)std::abs(task.pcm[i]));
display->SetMouthEnvelope(peak >> 8);   // 0..127
为什么放这里：这是全链路唯一「已经解码完、即将送 I²S」的点——数据一定存在、时间戳一定对、且不额外解一次码。表情任务只消费一个 1 字节的值，用深度 1 的队列覆盖写就行，积压会自己丢弃，不会拖慢音频。
不要在这里做重活：包络计算只是取绝对值最大值，一次遍历几百个样本，成本可忽略。千万别在这里加 FFT、加平滑滤波以外的任何处理——这个线程优先级只有 4，一慢就爆音。

八、优先级：谁可以打断谁

优先级层规则
P0FatalError / OTA抢占一切，不可被覆盖，只由状态机解除
P1L0 状态表情状态机迁移时立即接管；P1 生效期间 L1 情绪被挂起而非丢弃
P2L1 情绪表情持续 3–5 秒后自动回落；连续两次相同情绪不重播动画（避免抖）
P3L2 微动画永远在跑，但会被 P0/P1 抑制（如 OTA 时停止眨眼）
一个必须写的防抖：情绪串在流式输出里可能连续来好几个（happy→laughing→happy）。规则是「同一预设 800ms 内不重启动画」，否则脸会抽。

九、附带价值：把表情当 AEC 的诊断仪表

你正在查「自己说话时被自己打断」的问题。表情系统做好后，这个故障会变得肉眼可见：

现象说明
它说话时脸突然闪一下「惊讶」又回到聆听说明收到了 provider_vad_start 打断 → 自打断正在发生
正常说完整段，脸平稳回到平静这一轮没有被误打断
脸在「思考」卡很久不进入「说话」云端首包延迟问题，不是设备问题
实用做法：调试期给被打断加一个只有调试版才显示的小标记（屏幕左下角一个红点）。坐在对面看十轮对话，就能估出自打断率，比翻日志快一个数量级。量产版关掉。

十、分期建议：先做 8 个，别一次做 27 个

阶段做哪些目标
MVP
1–2 天		平静、聆听、思考、说话（含口型）、开心、难过、惊讶、错误能让一轮完整对话跑通并看懂。这 8 个覆盖了 90% 的实际停留时间
V1
+2 天		补齐剩余 7 个情绪 + 配网/连接/升级/低电/充电产品级完整度
V2
后续		喜欢、得意、搞怪、疑惑等「性格化」表情 + 待机小动作IP 感：让它有性格，而不是有功能
顺序不能反：先做「状态表情」，后做「情绪表情」。因为状态表情决定可用性（用户得知道它在听还是在想），情绪表情只决定可爱度。反过来做，会出现「表情很萌但不知道它在干嘛」的半成品。
