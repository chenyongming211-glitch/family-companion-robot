# Observer tail assessment — original 7bee4db

**Verdict: [P2] The reset rejects old AFE/encode output, but does not provide an observer auto physical-tail exclusion boundary.** This is a source-evidenced gating gap; it is not evidence that a measured device actually uploads intelligible residual echo.

All prepared-source references below are relative to the immutable `.superpowers/firmware-development-20261022/prepared-aec-commit-clean/` tree. Only the relevant complete functions and existing locked driver excerpts were inspected; no suites or executable tests were run, and no implementation source was edited.

## Evidence and transition

1. `main/application.cc:1071-1085` correctly enters `StartListeningAudio()` for a software-reference codec in auto mode, including the deferred queue-drained path. There is **no missing-start-call finding**. During Speaking, this adapter deliberately keeps voice processing active (`:1093-1100`) while its cloud uplink is disabled.
2. `main/audio/audio_service.cc:878-881,905-916` considers playback drained when decode/playback queues and decode/output in-flight flags are empty. `AudioOutputTask()` clears `output_in_flight_` after `codec_->OutputData()` returns (`:392-442`). This proves application write completion, not final physical TX completion.
3. The adapter's write (`main/boards/m5stack/stopwatch/software_aec_codec.cc:122-127`) goes through `esp_codec_dev_write` and the locked codec driver's `i2s_channel_write`. The existing exact-IDF excerpt `.superpowers/firmware-development-20261022/research/idf61-i2s-common.c:1605-1655` shows that `i2s_channel_write` returns after copying into DMA buffers, without waiting for those newly written samples' completed-TX callbacks. The configured six descriptors of 240 mono samples (`main/audio/audio_codec.h:15-16`) represent a nominal 60 ms DMA capacity at 24 kHz; this is a capacity calculation, not a measured tail duration.
4. `StartListeningAudio()` immediately calls `SetExperimentUplink(true)` (`main/application.cc:1127-1129`). Its following `EnableVoiceProcessing(true)` returns early because the observer processor is already running (`main/audio/audio_service.cc:790-792`). Thus the existing 120 ms input warmup path (`:339-343`, requested at `:800`) does not provide a new post-drain quarantine in this transition.
5. `UpdateExperimentGate()` clears encode/send queues and calls `SetOutputEpoch()` (`main/audio/audio_service.cc:206-220`). `SetOutputEpoch()` requests `ResetCapture()` (`main/audio/engines/afe_audio_engine.cc:252-262`). Processing resets its AFE input/output buffers and internal AFE buffer, and rejects old control/output epochs (`:432-493`). These are useful guards against already buffered AFE output and in-flight old fetch/encode work.
6. The reset has no dependency on a completed final TX sample, no minimum tail deadline, and no RX sample cutoff. Once the AFE reset finishes, `FeedCaptured()` accepts current capture-generation frames (`main/audio/engines/afe_audio_engine.cc:273-293`). Microphone samples acquired while the final DMA playback is still sounding therefore can be processed and tagged with the newly enabled output epoch. Capture stays active, so its hardware/capture generation does not establish a Speaking/Listening cutoff either. Pending RX blocks or an in-flight raw read from before the gate transition also remain eligible under that unchanged capture generation (`main/boards/m5stack/stopwatch/software_aec_codec.cc:128-143,173-207`).

## Consequence and limits

An AFE buffer reset cannot suppress sound that the microphone captures **after** the reset while TX still drains. It also cannot by itself identify old raw samples still upstream of AFE. The source allows those samples to become new-epoch cloud audio; whether the resulting PCM contains residual speaker echo depends on AEC convergence, alignment, acoustic coupling, DSP delay, and scheduling. No measured leakage, exact audible tail, or acoustic acceptance claim follows from this review.

This is relevant specifically to **observer auto**, whose ordinary cloud behavior should remain protected while AEC is being evaluated. Relying on unvalidated AEC to remove every residual tail sample weakens that separation. Valid realtime operation intentionally continues microphone processing during playback/interruption and should not receive this observer-only quarantine.

## Recommended correction

Keep observer cloud uplink closed through an explicit bounded tail boundary after software queues drain. Establish that boundary from completed DMA ownership/fencing, or a documented conservative bounded tail policy with fail-closed timeout; submitted samples must still never serve as AEC reference. Quarantine RX/in-flight raw samples through the same boundary, then acknowledge the AFE/output epoch reset and enable new cloud audio. Local microphone/reference observation can continue throughout. Do not stop the microphone or erase the physical reference tail to implement this.

A focused lifecycle regression should hold the final physical completions pending after software queue drain, make AFE reset complete immediately, and assert that observer new-epoch uplink remains closed; then advance the completion/capture boundary and verify that fresh audio is accepted while old raw/AFE/encode work stays rejected. The separate target/acoustic checks still determine the actual acoustic guard and delay.
