# 任务恢复：原生接口与真实链路发现

本报告记录2026-10-23机器合成输入、真实千问与回环模拟设备的调查。没有手表、麦克风录音、喇叭播放或真实I2S回报。输出文字、帧数和模拟采样不能作为准确接续或声学验收。

## 任务状态正确，还不等于实际续答已经归属

初版修复`9c066eb`及生命周期修复`071a23f`加入原请求/最新段分离、revision和生成前ACK。然而`071a23f`两次真实`resume-twice`样本都发现：第一次恢复块4正确绑定原任务，第二次中断也更新到块4；最后一次恢复块7虽然生成完整1–50，却没有再次绑定，暂停记录仍指向块4。

两个驱动均返回`transport_completed`。新增[归属检查器](../../tools/voice-audit/check_resume_ownership.py)均返回失败：`missing_successful_resume_binding`和`final_resume_not_owned_by_original_task`。这两次不能计为状态修复通过，更不能计为精确接续通过。用户在合成输入中明确允许位置未知时从一重读，本轮没有给定已播数字oracle。

私有证据位于`artifacts/resume-state-alignment-20261023/`：`final-resume-twice-delayed*`、`diagnostic-routing*`。两次均人为延迟中断final五秒，持续上行语音/静音，不模拟回声。

## 旧版本号和缺失的恢复操作已实测出现

隔离代理仅记录工具名、允许的action、版本号和结果，不记录原始参数/正文/音频/凭据。`diagnostic-routing-proxy.jsonl`显示：

1. 模型第一次以`expected_revision=2`请求resume，网关返回`revision_mismatch`。
2. 模型查询得到revision3，再请求resume3才成功；因此块4正确归属。
3. 第二次中断后，查询返回revision118、最新块4。
4. 最后续答没有再调用resume，却直接生成完整数数；块7保持未绑定。

所以不能把“已向模型注入最新状态”当成“模型一定正确提交状态变更”。后续实现应把归属判断放在语音放行之前，并由网关应用捕获的任务身份/版本，避免要求模型复制数字版本。

## 接口回显不能代替实际强制能力

真实原生配置测试：

| 请求/场景 | 实测 |
|---|---|
| `session.tool_choice="required"` | session.updated接受并回显required |
| 命名function对象形式tool_choice | 返回Invalid session.update payload |
| required + 故意要求“不要调用工具，只回答二” | completed，零工具调用，生成80640字节PCM |
| 正常专用路由提示词，仅提供路由工具 | 正确调用side，未生成音频 |
| 全程保持text/audio模态，路由结果后恢复普通生成设置 | 完成后续音频76800字节，生成文字“一加一等于二。” |

`required`不能作为网关放行的唯一依据。必须检查实际路由函数及其参数，缺失/失效时丢弃该阶段输出，有限重试并失败关闭。路由阶段不应发出设备控制。

另一次text-only路由后切回text/audio的单样本虽有配置ACK，后续completed却没有音频。本轮没有完整诊断其事件内容，不能泛化为所有模型都禁止切换；候选选择保持原有模态，并在Go端丢弃路由阶段音频，避免依赖尚未证实的切换行为。

相关字段须以实际能力为准；[官方客户端事件文档](https://help.aliyun.com/zh/model-studio/client-events)没有给出上述required的强制执行承诺。本轮记录了请求、回显和实际生成三层证据。

## “只答应不数”是另一个仍待处理的现象

相同合成请求在`9c066eb`第一次只生成“好的，我这就从一读到五十”，第二次则完整1–50。隔离运行原正式版`d68ec44`同样出现只答应不数。`071a23f`普通完整播放样本生成1–50（586帧）。

这说明该现象在旧版也能出现，不能据此认定本轮门控造成；也不能凭一次成功宣称履约已经稳定。各样本不是随机配对实验，不提供成功率估计。任务归属、模型履约、文字对齐和现场声音必须分别验收。
