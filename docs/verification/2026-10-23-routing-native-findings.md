# 任务恢复：原生接口与真实链路发现

本报告记录2026-10-23机器合成输入、真实千问与回环模拟设备的调查。没有手表、麦克风录音、喇叭播放或真实I2S回报。输出文字、帧数和模拟采样不能作为准确接续或声学验收。

## 任务状态正确，还不等于实际续答已经归属

初版修复`9c066eb`及生命周期修复`071a23f`加入原请求/最新段分离、revision和生成前ACK。然而`071a23f`两次真实`resume-twice`样本都发现：第一次恢复块4正确绑定原任务，第二次中断也更新到块4；最后一次恢复块7虽然生成完整1–50，却没有再次绑定，暂停记录仍指向块4。

两个驱动均返回`transport_completed`。新增[归属检查器](../../tools/voice-audit/check_resume_ownership.py)均返回失败：`missing_successful_resume_binding`和`final_resume_not_owned_by_original_task`。这两次不能计为状态修复通过，更不能计为精确接续通过。用户在合成输入中明确允许位置未知时从一重读，本轮没有给定已播数字oracle。

私有证据位于`artifacts/resume-state-alignment-20261023/`：`final-resume-twice-delayed*`、`diagnostic-routing*`。两次均人为延迟中断final五秒，持续上行语音/静音，不模拟回声。

## 旧版本号和缺失的恢复操作已实测出现

隔离代理仅记录工具名、允许的action、版本号和结果，不记录原始参数/正文/音频/凭据。`diagnostic-routing-proxy.jsonl`显示：

1. 模型第一次以`expected_revision=2`请求resume，网关返回`revision_mismatch`。
2. 模型查询得到revision3，再请求resume3才成功；因此块4正确归属。
3. 第二次中断后，查询返回revision118、最新块4。
4. 最后续答没有再调用resume，却直接生成完整数数；块7保持未绑定。

所以不能把“已向模型注入最新状态”当成“模型一定正确提交状态变更”。后续实现应把归属判断放在语音放行之前，并由网关应用捕获的任务身份/版本，避免要求模型复制数字版本。

## 接口回显不能代替实际强制能力

真实原生配置测试：

| 请求/场景 | 实测 |
|---|---|
| `session.tool_choice="required"` | session.updated接受并回显required |
| 命名function对象形式tool_choice | 返回Invalid session.update payload |
| required + 故意要求“不要调用工具，只回答二” | completed，零工具调用，生成80640字节PCM |
| 正常专用路由提示词，仅提供路由工具 | 正确调用side，未生成音频 |
| 全程保持text/audio模态，路由结果后恢复普通生成设置 | 完成后续音频76800字节，生成文字“一加一等于二。” |

`required`不能作为网关放行的唯一依据。`4e785d6`尝试在同一会话检查实际路由函数，并压制其音频；独立审查指出，未播内容仍可能留在上游上下文中。`1bdc325`因此改为一旦出现路由正文就立即失败关闭，不再复用该上下文。路由阶段不应发出设备控制。

另一次text-only路由后切回text/audio的单样本虽有配置ACK，后续completed却没有音频。本轮没有完整诊断其事件内容，不能泛化为所有模型都禁止切换。后续选择独立分类连接，不再切换主语音会话的角色或模态。

相关字段须以实际能力为准；[官方客户端事件文档](https://help.aliyun.com/zh/model-studio/client-events)没有给出上述required的强制执行承诺。本轮记录了请求、回显和实际生成三层证据。

## “只答应不数”是另一个仍待处理的现象

相同合成请求在`9c066eb`第一次只生成“好的，我这就从一读到五十”，第二次则完整1–50。隔离运行原正式版`d68ec44`同样出现只答应不数。`071a23f`普通完整播放样本生成1–50（586帧）。

这说明该现象在旧版也能出现，不能据此认定本轮门控造成；也不能凭一次成功宣称履约已经稳定。各样本不是随机配对实验，不提供成功率估计。任务归属、模型履约、文字对齐和现场声音必须分别验收。


## 同会话路由候选被真实链路否决

`1bdc325`完整Mac及精确源码Linux测试、race、vet和构建通过。然而真实`resume-twice`在首次旁支数学题时，千问立即输出非空音频转写，违反路由阶段约定；保护逻辑以`paused task routing generated content`关闭，未放行语音、未应用任务变更。该候选没有部署。证据为`final-required-routing.json`及其gateway/proxy记录。

同一轮更明确的合成数数指令确实触发1–50并进入中断，因此本次能定位到路由，而不是此前“只答应不数”导致测试尚未到达断点。先前那条早停失败仍保留为`required-routing-pre-fix.json`，不能算路由成功或失败的证据。

## 独立文本分类的可用协议已实测

新的短会话仅接收已有转写文本和原请求JSON，不发送音频，不请求ASR、不提供工具。主语音会话不参与分类。实测发现：

- 仅设置session.instructions、无输入再请求response，会被拒绝；必须在`response.create.response.instructions`中携带本次分类任务及数据。
- 在无音频的独立会话要求函数调用，可能只返回形似工具调用的普通文本，不能把它当成实际function事件。
- 去掉工具要求，明确要求只输出一个`side/resume/discard/replace`枚举，12条机器构造转写均给出匹配枚举，completed，单次端到端约332–423毫秒。

测试包含数学插话、明确继续/重读、查询暂停原请求、音量控制、暂不继续、放弃、改讲故事、唤醒问候和询问进度。每条使用新连接，结果保存在`isolated-router-enum.json`。这是小样本协议可行性，不是稳定成功率或手表测试。

因此最终实现改为独立异步分类：只接受严格枚举；带输入身份、任务身份和revision回到Go事件循环复核；迟到结果失效，有限重试；通过后再同步主会话快照并等ACK。分类文本不进入主会话。完整候选的链路验收和部署结果见本轮综合报告。

## 位置未知时，自行重读仍是失败

状态修复后的`d210811`通过两次恢复归属，但另一个普通“继续数”真实样本仍自行重读1–50，没有先问起点。这不能作为准确接续或未知位置退路的成功证据；该候选没有部署。

进一步将独立文字协议扩展为side/resume/restart/resume_from/discard/replace，并增加网关保存的awaiting_resume_choice。第一版14条中13条符合预期：未在等待选择时，单独数字仍被误判为起点。明确该边界后，相同14条实际原生请求全部符合预期，约331–540毫秒；两版结果均保留。这仍是小样本协议验证，不是成功率保证。

固定澄清句“我还不能确认刚才停在哪儿。请告诉我从哪里继续，或从头再来。”通过原生response.instructions生成，两个独立样本转写匹配，输出PCM约6.80秒和6.24秒。实现据此在网关暂存短回复，待完整转写、音频结束和成功状态均通过后才发给设备；不能仅凭提示词声称模型遵守了约定。完整集成和发布结果仍以[综合记录](2026-10-23-resume-state-and-alignment.md)为准。

最终`07c6549`的完整原生澄清/用户选择测试通过，且双中断两次恢复继续归属同任务。另保留一个进入澄清后，0.87秒快速单独数字未触发语义VAD的整轮失败；直接原生PCM对照手动提交可转写，稍慢版本可由语义VAD转写并通过完整场景。它发生在任务分类之前，没有据此修改网关路由或生产VAD参数。具体样本与限制见综合记录。
