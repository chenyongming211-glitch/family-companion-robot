# 插话后“继续”只给短片段

用户反馈：播放中直接开口已能停播并回答新问题，但要求继续数时只给几个数，未到原目标五十。本轮因此暂停八轮验收，不将其记为八轮或十轮通过。设备已请求 realtime off，诊断关闭，保留普通对话；后续开发先在隔离实例验证，无需用户反复现场测试。

## 已确定的边界

八轮测试的服务器记录中有三次播放中 interrupt。随后几段短回复分别约6.26、4.94、3.74秒，均由上游 `response_completed` 后排空待播，再正常 `tts_stop`；没有新的 VAD/interrupt、缓冲溢出或上游错误。用户未给出八轮完整结果，因此三次控制事件不能直接扩写成八轮实际成功。

这几段短播放是模型生成了短回复，区别于窗口六的操作者收尾关闭实时模式，也区别于此前20秒缓冲上限导致的断线。元数据不含对话文字，只能结合用户反馈判断这些短回复的意图，不能从日志猜测具体念到哪个数字。

源码确认的上下文缺陷：打断重建上游时只设 `previous_reply_interrupted=true`，丢弃被打断的生成稿；算术等插话问题正常回答后，又清除该标记。因而无法在后续上下文中区分“原内容尚未讲完”和“旁支问答已讲完”。已有最近12条历史仍可能保留原用户请求，所以缺陷并不意味着每次继续都会失败。

旧版隔离真千问的单次“数到50→插话问一加一→继续数”实际可以从头数完50，进一步说明现场问题不是每次稳定出现；未把该单次对照伪装成修改前必定失败的结果。连续插话对照另行记录。

随后用完全相同的合成音频连续做四次原生语音插话及旁支算术问答，再要求“继续数”。旧版最后一段生成稿为“一、二、三、四、五、六、七、八、九、十”，下行79个60ms帧，约4.74秒后正常 stop；未到原目标五十。一次中间接续也仅生成二至十，因计划内后续插话而提前取消。真实 API 的重复场景因此已复现接续只给短片段，不能把其中间被人工计划打断的帧数当成自然结束的长度。

## 有界修复

继续沿用现有 Go 网关、千问原生语音、重连和输入重放，不修改 AEC/固件，不引入数数识别器或固定终点。

- 保留当前有效回复的流式生成稿；迟到/错误回复 ID 不得混入，新的回复与正常结束必须清除临时稿。
- 播放中被打断的稿件，以 `delivery=interrupted` 与 `generated_text` 加入时间顺序上下文，明确其未完整播放；不作为普通已播完的 `text` 保存。
- 后续小问题的完整回答不删除这条记录；记录共享现有12条、每条512字限制。临时生成稿最多2048字，不进入日志或磁盘。
- 明确完整内容/原范围/终点优先于普通简短问答偏好；仅在用户明确要求继续时恢复，不在回答旁支问题后擅自抢话继续。无法确定精确暂停字词时不编造已播放进度，必要时简短确认。

真实本地 WebSocket/Opus 回归在旧代码上复现两种失败：转写仍在流式输出、或整段转写已就绪时，被打断的稿件均从重连上下文消失。修改后两种场景均保留未播完标记，并在完成旁支答案、再次重连后继续存在；另验证错误 ID 隔离、上下文上限及元数据日志不暴露流式稿件。

完整 macOS `go test -race -count=1 ./...` 和 `go vet ./...` 已通过，现有 Darwin CGO LC_DYSYMTAB 警告仍在。Linux 与真实千问连续复验、发布身份及现场验收分别记录，不能仅凭软件回归宣称用户的接续体验已修复。
