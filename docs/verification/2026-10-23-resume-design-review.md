# 自动接续方案复核：公开实现与当前约束

2026-10-23复核。结论：按设备播放进度维护模型上下文的方向合理；把外部强制对齐直接定为唯一实现路径过早。此次为官方文档/源码和既有实测证据的复核，未重跑各框架端到端测试，未改变线上代码、固件、VAD或加入辅助ASR。

## 对我们现用千问的判断

本次从线上配置只读取非敏感模型名：qwen3.8-omni-flash-realtime。当前官方客户端文档未列conversation.item.truncate；输出音频转写事件未给逐字起止时间。此前真实500ms边界截断未收到有效truncated确认，且续答仍跟随生成稿；这不足以断言所有后端永远不支持，但足以让当前实现不依赖它。该实测未在本次重跑，见[LiveKit对照](2026-10-23-livekit-comparison.md)。

因此不能照抄OpenAI插件就假设具备上游音频历史裁剪，也不能通过换框架补出不存在的时间信息。当前Go原任务/版本/归属与设备I2S回报继续保留。

## 原方案需要修正的地方

1. **外部对齐是候选，不是其他框架共同必需的组件。** 原生可确认音频截断或提供方词时间戳可优先复用；在目前千问限制下仍需自行补定位能力。
2. **完整音频实验不能覆盖早停。** 原生生成可能在正文已领先时被取消，剩下半段音频和完整或超前正文。此前52个模型结果涵盖重复、后端与文本变体，并不是52轮准确接续验收。截断/静音也可产生貌似完整时间戳，不能用它们自动宣布覆盖。audio.done本身也不能证明正常完整生成，千问文档明确取消或不完整时也会发出。
3. **句级恢复同样需要可证实的音频边界。** 按标点切文本或按固定语速估计，不能证明那句话已经播放完。保守恢复可以重读当前词/句，不能把尚未播的部分当成已完成。
4. **资源与异步处理必须验证。** 本机对齐CPU峰值约4.07GiB，线上服务器总内存约3.64GiB；先验证所选部署方式的实际开销。停止播放和收新输入不能等待对齐。

## 补充更新：文字记录、上下文恢复与播放断点（尚未实施）

用户提出保存对话是否有助于记忆。本方案增加最小的文字记录与恢复能力，并将它与播放位置映射分开验收；持久化全文不能替代已播证据，也不会仅因写入数据库就自动成为模型上下文。

当前已实现的是设备连接内的临时状态：网关最近12条文字消息、每条最多512字符，以及原任务和暂停快照；这些有界文字供上游重建/后续生成使用，同一千问连接本身还有原生会话上下文。当前网关没有这些正文的持久化数据库，设备连接结束后不恢复本地缓存。以下为建议目标，尚未开启文字落盘或修改模型说明。

| 建议保存的内容 | 用途与事实边界 |
|---|---|
| 用户输入转写、时间及会话/输入身份 | 回查和恢复聊天；明确标为语音识别文本，不当作原始录音或无误原话 |
| 助手生成稿及对应响应/播放身份 | 回查模型输出；保留生成、下发、完整交付、中断等状态，全文不能自动成为已播正文 |
| 设备有效采样回报 | 保存实际数字播放证据及所属会话/播放块，不按生成稿长度猜进度 |
| 已验证的文字前缀或未知状态 | 给后续接续使用；记录依据与版本，用户指定起点单独标为用户选择 |
| 原任务、终点、最新播放段、放弃/替换状态 | 维持任务归属；恢复历史不能让已放弃或已替换任务重新激活 |

首阶段采用服务器本地的最小文字存储，建议正文默认保留7天、期限可配置并可手动清空；运行数据不进Git，原始录音不在本次记录范围。存储选择、配额及清理在实现计划中落实，不额外引入向量库或复杂个人偏好系统。

恢复必须是显式的数据流程：取回本设备关联的相关近期文字与未完成任务，形成有界上下文，等当前快照ACK后再生成。历史内容作为带来源的数据处理，不能提升为系统指令；中断全文仍按现有规则排除，只有验证过的已播前缀才可作为已说内容。唤醒后可以取回背景，但不自动执行旧任务；用户明确要求继续后再恢复。跨连接为新播放块分配新身份，旧会话的原始采样计数不套用为新块进度。

同时给模型提供网关真实能力状态：是否有本轮临时上下文、是否启用/成功保存持久化文字、是否有本系统音频留存。回答记录问题时依据这些事实，不笼统声称“完全不记录”或“永久记住”。这份说明仅覆盖我们自己的服务，不替云端供应商作留存承诺。

持久化使用有界的异步写入，不能阻塞停播和新输入。保存失败不得宣称已保存或可跨会话恢复；删除文字时同步清理衍生摘要及相关任务恢复数据。

## 更新后的推进顺序（尚未实施）

1. 先补文字记录、正确的交付状态及有界上下文恢复；验证重新唤醒、服务重启后能找回原任务，而不会把生成稿全文当成已播内容。
2. 同期开展下述强制对齐/输出辅助ASR离线对照，选择通过准确度和资源验证的定位方式。离线比较不等于给生产增加ASR。
3. 将可信文字断点写回同一任务记录与revision，再通过现有生成前ACK门控交给模型，实现无需用户报起点的接续；定位失败仍询问。
4. 用重复插话、跨会话恢复、显式放弃/替换、迟到final和存储失败做回归。数数检查原终点、不漏数字；叙述允许重读被截断句，但不能跳过未播内容。

记录与恢复的验收和断点验收分别给结果：能回忆“刚才要求数到50”不等于知道“实际已经播到8”；后者仍须有可验证的文字映射。

## 播放断点离线对照设计（尚未实施）

保留现有生产链路与未知时询问的退路。在同一批机器人输出音频上离线比较：

- A：已知正文的强制对齐。只对确有对应音频的范围提交已播文字，重点验证正文领先和音频提前取消时的拒绝/降级能力。
- B：识别实际已播机器人音频的辅助ASR，必要时匹配生成稿/时间戳。它也会误识别或产生额外开销；不能免除播放坐标标定、覆盖检查和置信度判断。离线比较不等于决定给生产加ASR。

两条路都以独立标注为真值，覆盖中文数数、普通叙述、数字/专有词、完整生成、很早取消、词/句中间打断、恢复后再次打断，以及设备队列落后与迟到final。比较最后完整单位的误差、漏读/重读、结果准备时间、CPU/内存与实际调用费用；不能只比较有无返回时间戳。

通过后再接入：有效设备final→校准坐标→可信文字前缀→原任务的最新revision→当前快照ACK→恢复。可信度不足保持unknown并询问。优先目标是无需用户报起点、保住原终点、不漏内容，允许重读被截断词或句。

本轮不据此提出框架迁移，也未承诺某个模型已经达到上述目标。实验数据依据见[现有对齐评估](2026-10-23-forced-alignment.md)和[多框架模块对照](2026-10-23-resume-framework-root-cause.md)。
