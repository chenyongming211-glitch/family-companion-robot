# 小满唤醒后立即待命：诊断与临时恢复

## 当前结论

用户报告唤醒后约1–2秒又回到待命。现场已复现：MultiNet识别到小满、设备连接并进入Listening、云端收到语音且生成音频；首批播放回报为`valid=false, played_samples=0`，Go拒绝无效I2S证据并结束会话，设备Speaking后立即Idle。

手表当时`DuplexReference`锁存`fault=3`（Cadence），参考资格为0。`PlaybackProgress::Complete`也会在DMA回调间隔超出8500–11500us时锁存硬件无效；连接重建不会清除此状态，只有新的硬件epoch会重新建立资格。因此，重说唤醒词或重连服务不能恢复这一现场。

这说明本次**唤醒后播放即断开**的直接原因，不证明最早那次“叫小满无响应”也必然由相同原因造成。最早一次被动查询仍是`eligible=1/fault=0`，故障锁存出现在后续观察中；触发Cadence的具体事件没有完整时序证据，不能归因用户拔插USB。

## 本轮动作与实测

- 保留现场原始串口、统计和有界诊断在忽略的私有目录，没有提交音频、配置、备份或固件产物。
- Go新增`playback_rejected`事件，仅保存协议校验后的状态、计数及固定本地错误代码；原有拒绝规则、会话行为、AEC保护和已播历史规则不变。
- 现场诊断版本捕获到`invalid_i2s_receipt`，当时`sent=7200, completed=0, raw_played_samples=0, valid=false`，随后会话结束。此前只有泛化`session_terminated`，无法区分此原因。
- 证据保存后，通过esptool复位运行，没有刷写或擦除flash/NVS。复位后`eligible=1/fault=0`，默认实时资格重新建立。
- 合成唤醒与身份问题完成实际I2S播放：84960/84960样本；随后真人数学问题回答五，实际I2S完成44640/44640样本，会话仍在。用户明确反馈“能正常回答并继续对话”。合成测试与真人结果分别记录，不作为长期声学准确率证明。
- 新诊断回归先失败（拒绝回报时丢失诊断证据）、加入记录后通过。云端全仓`go test -race ./...`、`go vet ./...`和`go build ./...`通过；原有opt-in边界测试未额外启用。

## 尚未解决及排除边界

**当前是复位恢复，不是故障自动恢复的根治。** 固件仍是54ec169，没有新增自动重置音频硬件或自动重启。必须继续设计并验证：故障撤销上行并关闭旧会话，确保旧播放安全结束/失效，再重建硬件epoch与AFE资格；不得直接强置valid、放宽时钟阈值或把下发量当实播量。

另观察到两次输入监听约300秒后结束，旧日志只记录`input_provider_failed`，没有提供商原始错误或PCM计数，不能断言断流或确认超时原因。只有`session_started`而无speech事件也不能证明无PCM输入。

固件`IsTimeout()`使用120秒应用数据活性，而Go原有20秒心跳是WebSocket控制Ping；这是兼容性缺口。但持续发送音频的主循环和`SendAudio`不调用`IsTimeout()`，故不能把“120秒后自动停止上传”当成已证事实。本轮没有凭此改变心跳。

锁定IDF的USB polling写入在FIFO无法发送时最多短时等待，之后丢字节；源码不支持“关闭串口造成永久stdout阻塞”。AFE empty/fetch timeout也不能单独证明断流：本轮故障后有界诊断仍观察到MR和AFE各推进256000帧，参考无效但没有缺包。

后续稳定性验收仍需覆盖长时间静置后的真实唤醒、输入监听失活后的重连、硬件故障注入与安全恢复。短轮恢复成功不能替代这些验收。
