# M5 播放期间无法插话

2026-11-10，用户两次反馈 M5「没有爆音，但不能打断」／「仍不能打断」。当前应用为已回读校验的 `624addd`，Go 为统一机器人 600ms 窗口版本。爆音听感只记本轮用户反馈通过；完整双向语音交互未通过。

## 后台与设备证据

09:01:33 开始的 M5 会话 `12778e193776899168b49c2e4cf1c3b3` 有六轮输入，六轮输出均完整播放，没有播放中取消。第三轮第一包至完成播放约 18.82 秒；相邻两次语音起点之间经过 22.91 秒，后台收到的上行样本只增加 3.90 秒。第五轮约 25.20 秒播放，相邻语音起点之间 72.23 秒，上行样本只增加 46.80 秒。该差值说明播放期间上行缺失，与用户无法打断一致；不是用户插话实际起点的延迟测量。

随后接上仅向云端转发的 M5 串口，读取 `aec_stats`，未刷写固件。USB 连接后原业务连接结束、设备出现新的启动时钟，因此不能将该次串口打开视为无扰动观察；后续现场复现基于这个新启动周期，不与上一会话混为一轮。

新周期在约两分钟待机观察中保持 `eligible=1 fault=0 rx_pending=1`。用户再次测试时，日志记录：

- 设备时钟 180132ms：`idle -> connecting`。
- 随后 M5 软件参考采音队列 `fault=4`（`Overflow`），`rx_pending=16`；`tx=rx=4055040`，`paired=4050960`，故障计数 1。
- 183402ms：WebSocket 握手完成，总计 3160ms；183452ms：进入 listening，随后两次记录关闭设备 AEC，并退回 idle。
- 重试后仍沿用该已锁存的参考故障；用户反馈仍不能打断。后续输出发生在降级状态，不能作为正常 AEC 下的插话验收。

这是已观察到的采音溢出及降级链路。日志尚不能单独证明连接耗时中是哪一个锁或任务阻塞了采音；修复前应进一步核对连接期间的采音生命周期，避免放宽故障保护或扩大播放窗口掩盖问题。

私有原始串口记录仅保存在云端 `/var/backups/family-robot/m5-bargein-20261110/`；无音频采集，日志不进入 Git。微雪未刷写，Go 播放窗口、设备绑定与历史权限未修改。

## 共用生命周期修正

主任务与采音任务均固定在 CPU0，优先级分别为 10 和 8；WSS 连接在调用任务中同步完成 TLS。它们构成连接阶段阻塞采音的可能链路，仍不能排除 AFE feed／队列锁等其他停顿来源。

`0024-s3-connect-capture.patch` 只在成功进入 Connecting 的公共 `SetDeviceState()` 中同步关闭 managed capture 的 voice／wake 请求。物理 DMA 继续运行，现有 `CaptureEpoch::Pause()` 保留 wake generation，冻结唤醒包可先上传，再通过已有的当前 capture／通道代次握手恢复 realtime。没有扩大 RX 队列、取消故障锁存或改变 AEC／600ms 参数。

不能只改 UI 状态 handler：同轮已有 SCHEDULE 位时，新创建的网络 continuation 可能先于下一轮 STATE_CHANGED 执行；已开通道的唤醒路径也会直接继续。因此测试直接调用实际 continuation，而不预先派发 UI handler。

新增主机回归调用实际生产状态切换、连接／唤醒 continuation，配合真实 DuplexReference、CaptureActivation 和 WakeBatchValid：模拟连接阶段两秒无 Take、物理 DMA 持续运行，旧源码两组 S3 标志均退出 19，报告仍授权采音导致 RX 积压；修正后两组均通过。覆盖已开／新通道、暂停期间冻结唤醒包有效、恢复后旧包失效、连接失败回到待机唤醒、拒绝的状态切换无副作用、播放时 realtime 保持采音、既有 fault 不清除及普通 codec 行为保持。既有 fresh-capture 代次回归另行保留。

第一次测试夹具编译错误和第二次 ASan 预加载错误均保留，不作为有效 RED；有效记录为云端 `connect-red-v3.log`，GREEN 为 `connect-green.log`。测试使用任务／服务／板卡替身，不能证明具体 TLS 调度原因或替代真人插话。独立代码审查没有阻塞项。
