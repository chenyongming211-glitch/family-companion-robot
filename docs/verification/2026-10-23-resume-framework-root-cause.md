# 准确接续：根因与扩展开源对照

这轮不仅复核LiveKit，还检查此前已实际运行的千问官方Qwen-Live-Harness证据，新增Pipecat、TEN和小智Python服务端的实际模块实验，并完成8次真实千问上下文消融。结论是：**缺少“实际已播文字→原任务进度→下一次模型输入”的可靠闭环；自研网关还存在状态同步及恢复归属缺口。单纯保存完整聊天记录或换一个框架，无法补出这些信息。**

本轮没有修改Go/固件产品实现、替换线上框架、刷机、播放声音或加入辅助ASR。提交内容是诊断工具与证据报告；准确接续没有记为已修复。

## 三类证据分别说明什么

1. **信息缺失**：已有设备采样回报不等于文字位置；当前千问输出事件未返回可用逐字区间。8次合成历史消融中，仅删生成稿或自动附原目标但位置unknown，仍没有确定下一数字。人为提供“已播完1–8”后，两条生成转写均连续9–50。这证明本样本有明确断点时具备续数能力，不能证明生产音频映射、普遍可靠性或哪个单字段起效。
2. **我们的代码缺口**：重连只发送近期history，暂停任务依赖模型可选工具；迟到final只更新本地；同一任务恢复后再次被打断仍保护首次播放块，缺少resume关联；有界history淘汰后原目标仅留在工具内。三项回环characterization已经直接核验这些行为。它们不应全部归咎于模型，也不是每次短流程失败的同一直接原因。
3. **框架机制差异**：Pipecat在有字词时间戳且时钟同步时能形成已释放文字前缀，但模拟sink落后时仍会超前。TEN和小智所测路径保存的是生成前缀。取消、清队列、会话保持和文本对齐是不同能力。

## 对根因判断的限制

完整生成稿能进入我们的模型上下文，但其出现不必然导致错误；保留它的oracle组也成功。移除它之后仍出现从3开始，不能以“删全文”关闭问题。未知位置时明确询问或重读是当前约定允许的回退，未达到无缝接续需求，但不能统称模型错误。

原任务自动注入与工具调用不是同一个变量；本轮非oracle每组第一条都查询工具、第二条没有查询，不能单独量化自动注入收益。oracle也是同时提供文字和数字断点的冗余信息包。每条件仅两条、固定顺序，未验证服务端seed确定性，不报告成功率。

新增框架测试只证明其所测模块的历史/中断行为。模拟sink接收不是实际可听；数据类型里有word timestamp也不证明生产链路使用它。TEN另有一个锁定Python依赖组合下的中断校验异常，已单独保留，但它不是我们线上故障的根因。

## 推荐的修复顺序

先补明确的任务生命周期：原任务身份/目标独立保存，模型恢复前获得最新已结算状态；区分旁支回复与继续原任务，后续中断应推进该任务的新播放段。这个阶段无需辅助ASR，但单独做完仍不能保证准确下一字。

然后验证输出文字与设备解码/播放坐标的对应：只有可信字词区间和有效最终播放前缀相交，才提交已播文字。可以复用Pipecat的时间戳/迟到隔离思路，但必须按我们的设备回报约束释放，不能照搬接包墙钟。当前模型没有对应字词区间时，继续单独评估音频对齐的可行性；不能先凭比例猜位置或默默更换整条模型链路。

前两项建立后，再把暂停目标和已播前缀作为明确状态交给模型，并用重复插话/恢复、长旁支、有/无查询、生成先完成而设备未播完等用例验收。继续保留“位置未知”的真实状态，避免将实验中的8硬编码成产品规则。
