# 2026-10-21 StopWatch 控制与音频调度修复验证

状态：修复已部署；真实千问及模拟设备验证通过，实机控制与亮度语音确认已验收；偶发杂音暂未复现。

用户已确认最小修复范围：接通现有小智固件的音量、屏幕亮度/息屏工具，执行后读取状态核实；杂音依据音频证据单独处理。

## 已确认根因

旧网关忽略 MCP 消息，千问会话没有注册设备工具，因此模型的口头确认没有硬件执行依据。

旧音频调度使用每帧 `now + 60ms`，微小 tick 抖动会累计推迟发送。旧实机抓包中多段音频平均间隔为 64—65ms；一段 168 帧音频的首尾间隔为 10789.9ms，理想值为 10020ms。它可能导致播放缓冲缺音，尚不能证明是所有呲呲声的唯一根因。

## 修复内容

固定工具发现、严格整数参数校验、设置后状态核对、超时与失败结果、重复请求防护及打断后旧轮次清理。仅向模型返回音量和亮度，不传设备网络信息。

音频按原定时间线推进，明显停顿或缺音时重新设定锚点；最后一帧另按实际发送时间保留完整 60ms。工具独占的父回复不发出无音频的停止事件。

## 真实手表验证

保留小智 v2.5.2，无需重新刷机。本次实机 MCP 初始化与工具发现已通过；真实状态回读音量80、亮度50，与用户现场确认一致。真实音量60已收到设置回执和状态回读60，恢复80也有回读。现场确认亮度实际能改变，但初版控制曾误报失败。原设置为音量80、亮度50。

实机发现并修正了亮度核对时机：v2.5.2 通过每5ms一档的定时器渐变，设置0后首读49、设置50后首读1，随后状态才到目标值。原逻辑把合法中间值立即判为失败。新版本在原有5秒总期限内，每100ms仅重读状态，设置指令仍只发一次。超时、异常状态、音量不匹配仍返回失败，取消会清理待发送的状态复查。回归、独立复核、Mac/Linux检查和真实千问渐变模拟均已通过，新版本已部署。用户现场确认“实际变化，回复也正确”，误报修复实机验收通过。真实状态序列包含目标30的45→30、目标0的28→4→0、目标50的5→29→50，以及目标100的51→75→99→100；每次设置只下发一次，目标未到达时仅复查状态。

现场反馈：音量最大时仍偏小，但旧小智云端也差不多小；本次没有更改数字增益或设备固件，最大响度的源头尚未定位，不能直接归因于本次网关。近期下行Opus解码无错误，一段语音峰值约-2.26dBFS，直接统一放大可能削波，尚未实施增益改动。用户暂时没有听到呲呲声，同时认为音量较小可能影响判断，因此仍记为“暂未复现”，不记为彻底消除。
