# “谢谢夸奖”反复重播与TTS失败恢复

日期：2026-10-24，基线`06bc026`。用户澄清：是助手提示从头重讲后才照做，并非要求清空聊天。

## 现场事实与复现

- 麦克风会话`main:11`共2段，首段确认播完，第二段准备失败。云端对应TTS请求`input_characters=1`、`pcm_bytes=0`，30秒超时。
- 后续2次resume触发代码提示“可以明确要求从头重讲”；随后4次restart都从首段重播，形成用户听到的“谢谢夸奖”重复。既有日志只含元数据，不能还原那个单字符究竟是什么，也不能声称是ASR听错。
- 合成示例“谢谢夸奖！😊”在旧切句下成为5字符话语＋1字符表情。真实TTS对正常话语返回音频，对单独表情未返回PCM并报错；受控SDK回归也确认旧代码确实单独请求表情。
- 同一旧客户端还发生写队列满时递归退出：`stopInternal`在设置closed前尝试向已满队列发送stop，再次进入fail。云端控制对端批量撤销的独立复现出现593次failure、0次closed，进程退出138。

## 改动

- 接纳不可变语音稿之前清理表情、变体选择符及纯装饰段；保留文字、数字及其同段的数学/货币符号和温度单位。纯表情输出在TTS之前拒绝。语音稿冻结之后仍按同稿、同句级检查点恢复，不在播放途中改稿。
- 显式“继续”遇到TTS准备失败时，只重试当前未播单位，保留同一任务/版本和已确认前缀。不会在后台自动重试；只有用户请求恢复时调用retry。移除引导从头重讲的错误提示。
- TTS准备失败发送非致命`turn.error`，界面显示本轮失败，麦克风与其他原稿继续保留。
- 原生退出先锁定closed状态，使用WebSocket关闭结束服务端会话，不再向饱和队列追加stop消息。

## 已验证

- 两项定向回归先失败后通过：不再单独合成表情；第二句首次失败后继续，仅第二句有第二次准备，第一句只准备一次，原稿revision不变且最终确认2句。
- 真实云端TTS对规范化示例返回65280字节PCM。另一次真实TTS＋人为单次第二句失败验证：第一句合成1次、第二句尝试2次、版本不变、最终确认2句。此层使用模拟回执，不作为物理播放证据。
- 修复后原生同一退出压力对端：仅1次failure、1次closed，进程按预期退出1，无递归崩溃。该用例不使用模型、麦克风或录音，云端临时对端只监听loopback18122。
- 云端Python完整119项通过，116.836秒；包含纯表情稿在TTS之前拒绝、旧unknown失败不后台重试及句级恢复回归。Mac构建和账本/麦克风/原稿恢复证明/启动器检查通过。
- 部署后的原生云端实连fixture通过：3句故事→播放中插话→旁支完成→恢复同一原稿`main:1 / revision1`并完成3句，最终ACK齐全，证据为CoreAudio实际回调。输入是合成WAV，不代替本次真人听感验收。服务刚重启、后端尚未ready时的首个探针曾在hello前失败；确认两服务health后再跑完整流程通过，没有把首个失败当成功。
- 只重启独立18010/18020服务，原8000进程仍为2261506。旧客户端已因递归退出断开，修复版需要新开测试会话，不声称接回已经丢失的进程内原稿。
