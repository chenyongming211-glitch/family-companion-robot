# 微雪600ms窗口后的插话回退

2026-11-07，用户反馈连续播放已无爆音，但机器人播放时无法打断。前一轮仅验收了完整长回复，未完成真人插话验收；600ms不能据此视作完整交互修复。

## 已核对的链路

当前Go构建`58c14cd-window600-release`，只对目标已鉴权微雪启用600ms；其它终端保持300ms。设备此前已恢复原产品ELF`5f2359074`。本轮不改Go窗口、模型、VAD、AEC、DMA或任务优先级。

最近目标会话`0605543cb860922b632120419655ffd2`有五个输入轮次，前四个回复分别完整播放约17.2、16.0、8.3、23.9秒；播放期间没有新的provider speech_started。第五轮有一次取消，252000样本在488ms完成可信drain。因此“无法打断”不能仅用窗口多出的300ms尾音解释。相邻语音起点间，Go交付的输入音频时长仅为墙钟的71%～85%；这不是识别率，也不提供用户实际插话起点。

源码中`InputData`与`OutputTagged`共享`lifecycle_`。旧输出方法在软件PCM队列满时，持有该锁调用`vTaskDelay(1)`，使采集线程无法读取ADC。扩大下发额度可让输出队列持续有积压，从而加重既有竞争；尚不能把锁竞争等同于所有现场插话失败的唯一原因。

## 回归与单变量实机控制

新增测试通过实际生产方法及真实互斥锁，填满12个软件播放块，令另一个线程调用`InputData`。旧代码在等待DMA腾空间时，采集无法完成，RED明确失败于`capture blocked behind a full playback queue`。修正只在等待队列空间时解锁，返回后重新加锁并执行原有代次／健康检查；测试GREEN。另覆盖等待期间硬件生命周期改变，保证旧代次输出退出。

首次运行ASan缺少预加载，不作为有效RED；修正ASan环境后，初版测试的DMA地址重复触发保护也不作为有效RED。最终六地址环模拟的RED／GREEN及15项微雪相关测试均在云端通过。第一次广组运行等待上游下载，受控停止后复用已校验的上游archive完成，未取消生产进程。

实机先使用此前已构建的六槽释放锁诊断候选，ELF`97cc768c80b5a12092d9b2efbff9e2408b6836ebe70a7b6c0aea0a999df9f5d1`；仍为优先级2、音量100、初始亮度50。八组全部完整、硬件fault=0。
